## 3. 四诀结论要点

### 3.1 明辨诀（朱熹 · 对抗审查）— 22 条问题

- **P0 × 5**：①老病灶自动复活链路 ②主题数三方打架 ③灰度/监控不可执行 ④§3.5「≤120KB/片」被实测证伪 ⑤§11 bundle 预算对 `public/` 静态分片**结构性失明**
- **P1 × 13**、**P2 × 4**
- **独立发现**（主控事实表之外）：预取相邻分片无效、50MB 源数据随 dist 部署、`globalId` 无生成任务、检索引擎迁移遗漏、bundle 预算覆盖盲区
- 判语：*「最大的失败模式不是排期，而是旧 P0 有完整的复活链路（脚本 + vite 钩子 + 已 tracked 生成物三件套都还在），而方案把它们当成『已归档』。」*

### 3.2 破妄诀（慧能 · 假设穿透）— 7 条妄执

- **W1（P0）**：「分片按需 = 传输量下降」是未实测假设。实测最大片 gzip 1159KB；《心经广义》2651 个命中术语**散布 72/72 片**，连续阅读查词必然散列 → 「按需」退化为「高频多拉」，弱网下 8s 超时会**复现旧版同一症状「查不到释义」**
- **W2**：scope M7 要求「释义级」四级匹配（P0），plan 索引不含释义，且已判 `dict-defs` 弃用 → **无实现载体**
- **W3**：「重写 = 解决质量」前提证伪——99.4% 体积集中在一个生成物，其余 39 文件仅 124KB
- **W4**：离线卖点被静默牺牲（v3.1.0 首载后断网可查，v4.0 按需拉分片后断网即无释义）
- **W5/W6/W7**：plan↔scope 三处硬冲突；病灶自动复发链路；1 人项目引入 5 类自维护规则

### 5.1 外部参照与「更轻的替代路径」（知彼诀；**情报，供裁决 A 参考，主控未据此改判**）

1. **sql.js-httpvfs**（SQLite 静态托管 + HTTP Range + B-tree 索引）：单次索引点查询约 **7 次 page read（KB 级传输）**，复杂查询 130–270KB。对照本方案，「索引 + 48MB 分片 + 构建期生成 + IndexedDB 编排」这四件套**或可整体省掉**——**这是比方案现有设计更轻的备选路径**，值得在裁决 A 时一并权衡。
2. **萌典 moedict-webkit**（已知最接近的同类产品）：索引与数据分离，**按首字码点 mod 1024 分桶**，而非定长 500 词 —— 直接对应建议 3「改切分键」。
3. **Vercel 压缩**：CDN 自动 gzip + brotli，json 在自动压缩列表内；本项目实测 47.5MB → brotli 15.7MB。
4. **未确认**：Vercel 对非哈希文件名（本项目分片命名方式）的默认缓存头行为。

### 7.1 最高杠杆改进项：新增「已裁决废弃项清单 + 构建期存在性断言」

> 破妄诀提出、明辨诀附议，主控采纳为**本次会审第一优先改进项**。

**问题定性**：方案 §11 名为「防复发」，实为**「防再犯」**——它拦的是「将来有人写坏代码」，对「**病因重新被引入**」的覆盖率为 **0**。而本次会审的头号发现（P0-1）恰恰是病因复活，不在现有六道机制的拦截范围内。

**解法**：把「已裁决废弃」从**文档结论**升级为**机器可执行的断言**。建议 5 条：

```text
**A 类 · 绝对断言**（文件或钩子不该存在）

> ⚠️ **启用前提**：其中 2 条当前**为假**（`buildDictIndexPlugin` 仍注册、`public/dict-defs/` 仍存在）。须先完成建议 1 的清理动作再启用，否则断言一上就是永久红灯，很快会被当噪音关掉——那等于没有护栏。
```text
assertNoFile('scripts/build-dict-index.cjs')        # 20.8MB 病灶生成器
assertNoFile('scripts/build-dict-defs.cjs')         # 300 字截断版生成器
assertNoMatch('vite.config.*', /build-dict-index/)  # 自动复活钩子
assertNoFile('src/data/dictIndex.js')               # 病灶产物本体
assertNoMatch('.eslintrc.cjs', /dictIndex\.js/)     # 复活链路第四件
```

**B 类 · 棘轮断言**（ratchet：数量只减不增）
```text
assertTrackedCount('public/dict-chunks/') <= baseline   # 基线取当前实测 75，清理后下调
assertTrackedCount('public/dict-defs/')   <= baseline   # 基线取当前实测 3，清理后下调
assertNoFileInDist('*.json', size > 2MB)                # 补 §11 对 public/ 失明的洞
```

> **为什么 A、B 两类缺一不可**：绝对断言管「文件不该存在」，棘轮断言管「数量不该回升」。若只有绝对断言，后人加一条 `!public/dict-chunks/` 或重新 `git add` 一次，护栏即失效而 CI 不报错——这正是本次会审反复批评的「防复发机制自我失效」换了张脸。

**C 类 · 基线治理**（明辨诀提出，防护栏自我失效）
- 基线存入 `scripts/guard-baseline.json`，**入库管理，只能人工显式下调**
- **基线按当前实测值登记（75 / 3），不得直接设 0**：否则断言一启用即恒假、很快被当噪音关掉；随清理 PR 逐步下调至目标 0。护栏的目的是「防新增」，不是「一上就全红」
- **基线文件缺失或被删 → CI 判失败**，不得当作「无基线、跳过」。基线文件是护栏存在的前提，需要一条针对自身的存在性断言（与 A 类同型，成本是同一脚本内一行 `fs.existsSync`）——否则删掉基线文件即可让整道护栏消失且不留痕，与反复批评的「防复发机制自我失效」是同一失效口
- **CI 不得自动更新基线**——否则护栏退化为「永远通过」
- CI 中该步**禁止** `|| true` 与 `continue-on-error`
- 基线下调需走提交并说明「清理了什么、为何下调」；**上调需用户显式批准**

**配套硬要求**：方案 §8 的 12 个任务中**必须显式新增一条** `git rm -r --cached public/dict-chunks public/dict-defs`。缺了这一条，上面第 4/5 条断言**恒为假**（文件已 tracked，`.gitignore` 对其无效），断言会永远通过而问题永远存在。

**为什么杠杆最高**：成本 ≈ 0.2 人天，但它把「本次会审的全部结论」固化成不可绕过的事实——否则三个月后重读方案的人，仍会面对脚本仍在、钩子仍在、生成物仍在的同一个仓库。
