# v2.0 → v2.1 变更说明

> 完成日期：2026-05-02
> 基于：docs/plans/v2.1-integrated-design.md

## 1. 背景与目标

般若佛经阅读器 v2.0 方案完成后，开展了 50 个调研任务，覆盖 Vue 3 架构、IndexedDB 存储、高亮引擎、MDX 解析、Markdown 格式、v1.0 逆向分析、前端安全、Service 层抽象和禅意设计落地等核心领域。

v2.1 基于全部调研结论，对 v2.0 方案进行修正和补充，核心目标：

1. **固化调研结论**：将 50 个调研任务的决策固化为方案文档
2. **消除 v2.0 未决项**：解决 v2.0 中 10 个待决策问题
3. **修正方案偏差**：根据调研数据修正 v2.0 中不准确的估算和设计
4. **补充缺失模块**：增加安全策略、设计 Token 系统、Service 接口规范等 v2.0 遗漏内容

## 2. 变更清单

### 2.1 架构变更

| 变更项 | v2.0 | v2.1 | 原因 | 影响 |
|--------|------|------|------|------|
| **Service 层抽象** | JavaScript 类，直接耦合实现 | TypeScript 接口 + 工厂模式，IndexedDB/REST API 双实现 | T-48 调研确立接口抽象规范，支持未来后端切换 | Phase 1 增加 TS 接口定义和工厂模式实现，开发工作量增加约 4h |
| **Store 大型数据管理** | 未明确限制 | 明确"大型数据不进入 Store"，章节内容/释义全文由 Service 层管理 | T-01 调研结论：Store 序列化后不超过 500KB，否则影响性能 | Store 设计需重新审查，确保只存轻量状态 |
| **Trie 构建位置** | 主线程 | Trie 构建放 Web Worker，匹配放主线程 | T-05 调研：构建 50-80ms 阻塞主线程，匹配仅 3-8ms 无需 Worker | Phase 1 增加 Worker 通信层开发，Trie 模块结构变更 |
| **高亮渲染方式** | 未明确 | HTML 字符串一次性构建 + 段落懒渲染 | T-05 调研：innerHTML 比 createElement 快 10-20 倍 | 高亮引擎实现方式变更，需新增懒渲染组件 |
| **MDX 分级策略** | <5MB / >=5MB 两档 | <5MB / 5-10MB / >10MB 三档 | T-06 调研：5-10MB 场景需预解析索引但释义懒加载 | MDX 解析器增加中间档处理逻辑 |
| **MDX 切割策略** | 10MB 限制，超出切割（未实现） | 不切割，>10MB 直接模式 + 用户提示 | T-06 调研：自动切割技术风险高、实现复杂度大 | 移除切割方案，简化 MDX 处理流程 |
| **存储降级策略** | 未提及 | 三级降级：IndexedDB → localStorage → 内存 | T-04 调研：iOS Safari 50MB 硬限、隐私模式等场景需兜底 | 新增 storage/fallback.js 模块，所有存储操作需兼容降级 |
| **安全策略** | 未提及 | DOMPurify + CSP + 文件验证 + 恶意扫描四层防护 | T-14 调研：用户上传 MDX 含 XSS 风险 | Phase 3 增加安全模块，Phase 4 配置 CSP |
| **Markdown 渲染引擎** | marked（未确定） | markdown-it + DOMPurify | T-07 调研：markdown-it 插件生态更丰富，SSR 兼容更好 | 替换依赖，渲染组件实现变更 |
| **HTML→Markdown 转换** | 未提及 | turndown + 自定义规则（保留 ruby/梵文标签） | T-06/T-07 调研：浏览器端唯一可用方案 | MDX 解析流程增加 turndown 转换步骤 |
| **设计 Token 系统** | CSS 变量（v1.0 延续） | 完整 `--zen-*` Token 系统，日间/暗色/护眼三主题 | T-49 调研：v1.0 配色不合格，需禅意重构 | Phase 1 新增 tokens.css 和 Vant 主题覆盖 |
| **正文字体** | 黑体 | 宋体 | T-49 调研：宋体符合传统经书风格 | 全局样式变更 |
| **主题切换机制** | boolean `isDarkMode` | `data-theme` 属性（day/dark/eye-care） | T-49 调研：支持三种主题模式 | Settings 数据模型和 UI 组件变更 |

### 2.2 数据模型变更

#### 表结构变更

| 变更项 | v2.0 | v2.1 | 原因 | 影响 |
|--------|------|------|------|------|
| **dictionaries 表** | 独立的 `dict_config` + `dictionaries` | 合并为统一 `dictionaries` 表 | T-04 调研：两表功能重叠 | 简化表结构，减少 JOIN 操作 |
| **dict_term_lookup 表** | `dict_index` 表名 | 更名为 `dict_term_lookup` | T-04 调研：明确为 Trie 构建数据源，不含 definition | 所有引用该表的代码需更新表名 |
| **dict_entries 主键** | `key` | `key`（复合：`dictId::term`） | 明确复合主键设计 | 查询逻辑无需变更，但需在文档中明确 |
| **dict_entries 格式** | 纯 HTML | 增加 `format` 字段（`html` / `markdown`） | T-06/T-07：小词典存 Markdown，大词典存 HTML | 查询和渲染逻辑需检查 format 字段 |
| **dictionary_versions 表** | `dict_versions` | 更名为 `dictionary_versions` | 命名统一 | 所有引用该表的代码需更新表名 |
| **新增 file_cache 表** | 未列出 | 明确 `file_cache` 表（MDX 原文件等） | T-04 调研：13 张表之一 | 新增表结构和操作模块 |
| **新增 user_highlights 表** | 未列出 | 明确 `user_highlights` 表 | T-04 调研：13 张表之一 | 新增用户高亮标记功能 |
| **新增 statistics 表** | `reading_stats` | 更名为 `statistics` | 命名统一 | 统计模块代码需更新表名 |
| **新增 settings 表** | 未单独列出 | 明确 `settings` 表 | T-04 调研：13 张表之一 | 设置模块需从通用存储迁移 |
| **新增 sutras / sutra_chapters 表** | `sutra_index` / `sutra_content` | 更名为 `sutras` / `sutra_chapters` | 命名统一 | 经书模块代码需更新表名 |
| **新增 dictionary_chunks 表** | 未列出 | 明确 `dictionary_chunks` 表（大词典分块） | T-04 调研：13 张表之一 | 大词典分块存储逻辑 |
| **表总数** | v2.0 文档列出 9 张 | 统一为 13 张表 | T-04 调研完整验证 | IndexedDB 初始化代码需更新 |

## 3. 影响评估

### 3.1 对开发进度的影响

| 影响维度 | 评估 | 说明 |
|----------|------|------|
| **总工时变化** | 增加约 20-25h | 主要来自安全策略、Token 系统、TS 接口、降级策略等新模块 |
| **Phase 1 工作量** | 增加约 18h | Token 系统、TS 接口、降级策略、Worker 构建均为新增 |
| **Phase 2 工作量** | 增加约 13h | 高亮引擎细化、懒渲染、文件验证、迁移脚本 |
| **Phase 3 工作量** | 增加约 11h | turndown 转换、markdown-it 渲染、恶意扫描 |
| **Phase 4 工作量** | 增加约 6h | CSP、配额监控、图标替换 |
| **整体进度** | 延后约 1-2 周 | 若保持 4 周开发周期，需压缩 P2 功能或增加开发资源 |

### 3.2 对技术风险的影响

| 风险项 | v2.0 评估 | v2.1 评估 | 变化 |
|--------|-----------|-----------|------|
| MDX 支持耗时超预期 | 高 | 高（但三档策略降低不确定性） | 风险可控性提升 |
| Trie 内存占用过大 | 中 | 中（Worker 构建 + 分层 Trie 降低风险） | 风险降低 |
| iOS Safari 存储限制 | 未识别 | 高（已明确 50MB 硬限 + 三级降级） | 风险可见性提升 |
| XSS 安全风险 | 未识别 | 中（四层防护已规划） | 从盲区变为可控 |
| 禅意设计迁移工作量 | 未识别 | 中（23 项变更清单已明确） | 风险可见性提升 |
| TypeScript 学习成本 | 无 | 低（仅接口用 TS，实现用 JS） | 可控 |

### 3.3 对开发质量的影响

| 质量维度 | v2.0 | v2.1 | 提升点 |
|----------|------|------|--------|
| **方案可追溯性** | 弱（决策无依据） | 强（每个任务标注调研依据） | 开发时可快速回溯决策原因 |
| **安全性** | 无 | 四层防护（DOMPurify + CSP + 文件验证 + 恶意扫描） | 用户上传内容安全可控 |
| **兼容性** | 未考虑降级 | 三级降级策略 | iOS 隐私模式等边缘场景有兜底 |
| **可扩展性** | Service 层耦合实现 | TS 接口 + 工厂模式 | 未来切换后端 API 成本极低 |
| **设计一致性** | v1.0 变量延续 | 完整 Token 系统 + 三主题 | 禅意风格统一落地 |
| **性能可控性** | 目标值无依据 | 每个指标有调研数据支撑 | 性能优化有明确方向 |
