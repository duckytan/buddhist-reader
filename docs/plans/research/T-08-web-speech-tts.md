# Web Speech API TTS 引擎优化 调研报告

> 任务编号：T-08
> 完成日期：2026-05-02
> 基于：docs/PROJECT_V2_PLAN.md

## 1. 背景与目标

般若佛经阅读器 v2.0 需要为中文经文和梵文/巴利文咒语提供 TTS（文字转语音）诵读功能。Web Speech API（SpeechSynthesis）作为浏览器原生 API，零成本、无需网络、无调用限制，是首选方案。本调研旨在评估其在中文经文诵读场景中的实际表现，对比商业 TTS 方案，为 v2.1 TTS 功能模块提供技术选型依据。

核心调研问题：
- 各浏览器中文语音质量差异及最佳实践
- 梵文/巴利文（咒语、陀罗尼）的 TTS 支持现状
- 语速、音调、音量的经文诵读推荐参数
- 长经文断句与停顿策略
- 商业 TTS 与 Web Speech API 的性价比对比
- 离线可用性与降级方案

## 2. 浏览器 TTS 质量对比

| 浏览器 | 中文语音引擎 | 音质 | 离线可用 | 备注 |
|--------|-------------|------|---------|------|
| **Chrome (Windows)** | Microsoft Speech Platform / Google Cloud TTS | 中等 | 部分离线 | Windows 上使用系统 SAPI 语音；macOS 上调用系统语音（如 Ting-Ting）。音质中等，中文自然度一般，长文本可能出现 `onend` 不触发问题。语音列表丰富度依赖操作系统。 |
| **Chrome (macOS)** | macOS NSSpeechSynthesizer | 中等偏上 | 完全离线 | 可调用系统丰富语音（如 Ting-Ting、Sin-ji），音质较好。完全离线运行。 |
| **Edge (全平台)** | Microsoft Azure Neural TTS | 优秀 | 需要网络 | 使用微软 Azure Neural 引擎，支持 20+ 种高质量中文声音（晓晓、云希、晓伊等）。音质最佳，接近真人。需要网络连接获取云端语音。 |
| **Safari (macOS/iOS)** | macOS/iOS 系统语音 | 中等 | 完全离线 | 调用系统语音（macOS: Ting-Ting, Sin-ji; iOS: 系统内置）。音质一般，音色选择有限（通常 1-2 个）。iOS 需用户手势触发播放。rate 参数在 iOS 上不可靠，常被忽略。 |
| **Firefox** | OS 系统语音 / eSpeak | 较差 | 完全离线 | 依赖操作系统语音或 eSpeak 引擎。中文自然度欠佳，音色多样性不足。部分语言支持不完整，`onend` 事件可能不触发。 |

**关键发现**：
- Edge 的中文语音质量在所有浏览器中最优，得益于 Azure Neural TTS 引擎
- Chrome 在 macOS 上表现优于 Windows（系统语音质量差异）
- Safari 在 iOS 上存在 rate 参数被忽略的已知限制
- Firefox 的中文 TTS 质量最弱，不建议作为主力引擎
- 所有浏览器的语音列表均通过 `speechSynthesis.getVoices()` 异步加载，需监听 `voiceschanged` 事件

## 3. 梵文/巴利文支持

### 3.1 浏览器原生支持情况

| 浏览器 | 梵文 (sa-IN) | 巴利文 (pi) | 说明 |
|--------|-------------|-------------|------|
| Chrome | 不支持 | 不支持 | 无梵文/巴利文专用语音。可用印地语 (hi-IN) 语音近似朗读天城体梵文文本，但发音不准确。 |
| Edge | 不支持 | 不支持 | 同上。Edge 的语音覆盖 140+ 种语言，但不包含梵文/巴利文专用语音。 |
| Safari | 不支持 | 不支持 | macOS/iOS 系统语音不包含梵文/巴利文支持。 |
| Firefox | 不支持 | 不支持 | 无梵文/巴利文语音支持。 |

### 3.2 实际处理方案

由于浏览器不提供梵文/巴利文专用语音，项目中可采用以下策略：

1. **印地语近似朗读**：将梵文天城体文本的 `lang` 设为 `hi-IN`，使用印地语语音朗读。发音大致接近（同属印度语系），但不精确，尤其对梵文特有的连音规则（sandhi）和长元音处理不佳。

2. **中文音译朗读**：对于常见的咒语（如大悲咒、往生咒），使用中文音译文本（如"南无喝啰怛那哆啰夜耶"），用中文语音朗读。这是目前最实用的方案，因为：
   - 中文音译是汉传佛教的传统诵读方式
   - 用户熟悉中文音译的读法
   - 中文语音质量远高于印地语近似

3. **罗马化转写朗读**：将梵文转写为 IAST 罗马化文本（如 "namo ratna-trayaya"），用英语语音朗读。效果最差，不推荐。

**建议**：v2.0 中梵文/巴利文咒语统一使用中文音译版本配合中文语音朗读。保留原文天城体/巴利文显示，但 TTS 引擎使用音译文本。

## 4. 控制参数

| 参数 | 范围 | 默认 | 经文推荐 | 说明 |
|------|------|------|----------|------|
| **语速 (rate)** | 0.1 - 10.0 | 1.0 | 0.80 - 0.90 | 经文诵读宜慢不宜快。0.85 为推荐的默认值，庄重沉稳。用户可调范围建议限制在 0.6 - 1.2。Chrome 超过 2.0 可能被截断；iOS Safari 上 rate 参数不可靠。 |
| **音调 (pitch)** | 0.0 - 2.0 | 1.0 | 0.70 - 0.85 | 较低音调营造庄严、沉稳的诵读氛围。0.75 为推荐默认值。过高（>1.5）会失真，部分引擎在 pitch 超出正常范围时会调整 rate 来"补偿"。 |
| **音量 (volume)** | 0.0 - 1.0 | 1.0 | 1.0 | 经文诵读不需要调节音量。不建议低于 0.3，否则某些系统语音引擎会静默提升 rate 以维持可听度。 |

**经文诵读推荐预设**：

| 场景 | rate | pitch | volume |
|------|------|-------|--------|
| 日常诵读 | 0.85 | 0.75 | 1.0 |
| 慢速学习 | 0.70 | 0.70 | 1.0 |
| 快速浏览 | 1.00 | 0.85 | 1.0 |
| 咒语诵读 | 0.80 | 0.70 | 1.0 |

**浏览器兼容性注意事项**：
- 必须在 `speak()` 调用**之前**设置参数，之后修改无效
- iOS Safari 上 rate 参数经常被忽略，需在每次 `speak()` 前重新设置
- pitch 超过 2.0 或低于 0.5 时，部分引擎会强制调整 rate
- volume 低于 0.2 时，Windows 的某些语音会静默提升 rate

## 5. 断句策略

### 5.1 问题分析

Web Speech API 本身**不支持直接设置停顿时长**。浏览器会根据标点符号自动处理停顿：
- 逗号（，）：约 200ms 停顿
- 句号（。）、叹号（！）、问号（？）：约 400ms 停顿
- 分段符：约 500ms+ 停顿

但对于经文诵读场景，这种默认停顿有以下问题：
1. 经文中的特殊符号（如"卍"、"◎"）可能被忽略
2. 梵文咒语中的音译长句需要更长的句间停顿
3. 默念/跟读模式需要更大的停顿空间
4. 长文本（>500 字符）在部分浏览器中可能出现 `onend` 不触发或静默中断

### 5.2 推荐断句方案

**方案 A：按标点分段播放（推荐 v2.0 使用）**

```javascript
function splitByPunctuation(text) {
  // 按中文标点分割，保留标点符号
  const segments = text.match(/[^。！？,.!?]+[。！？,.!?]?/g) || [];
  return segments.map(s => s.trim()).filter(s => s.length > 0);
}

async function readWithPauses(text, pauseMs = 300) {
  const segments = splitByPunctuation(text);
  for (const segment of segments) {
    await speakSegment(segment);
    await sleep(pauseMs);
  }
}
```

- 优点：实现简单，兼容性好，每段不超过 100 字符避免长文本问题
- 缺点：停顿时间固定，不够智能
- 适用场景：日常诵读、咒语朗读

**方案 B：按语义层级分段（v2.1+ 增强）**

```javascript
function splitBySemanticLevel(text) {
  const levels = {
    'section': /【[^】]*】|第[一二三四五六七八九十]+[部分章品]/g,  // 段落/品
    'sentence': /[。！？]/g,   // 句子
    'phrase': /[,，;；]/g,     // 短语
  };
  // 按层级返回分段及推荐停顿时间
}
```

- 段落分隔符（"【】"、"第X品"）：停顿 800ms
- 句号/叹号/问号：停顿 500ms
- 逗号/分号：停顿 250ms
- 咒语行间分隔（换行）：停顿 400ms

**方案 C：SSML 精确控制（不推荐，兼容性差）**

```javascript
// SSML 仅在部分 Chrome/Edge 版本中有限支持
utterance.text = `<speak>你好，<break time="500ms"/>再见</speak>`;
```

- iOS Safari 完全不支持 SSML，`<break>` 标签会被静默丢弃
- 多数移动端浏览器不支持
- 不建议作为主力方案，可作为 Edge 浏览器的增强选项

### 5.3 长文本处理

- 每段文本建议控制在 **300-500 字符**以内
- 超过 500 字符的经文应按品/段落自动拆分
- 使用队列管理：前一段 `onend` 触发后再播放下一段
- 保存当前 utterance 实例，用 `speechSynthesis.pending` + `speaking` + `paused` 组合判断状态

## 6. 商业 TTS 对比

| 服务 | 中文质量 | 梵文支持 | 价格（每百万字符） | 离线可用 | SSML | 适用场景 |
|------|----------|----------|-------------------|---------|------|---------|
| **Web Speech API** | 中等（Edge 优秀） | 不支持（用中文音译替代） | 免费 | Chrome/Safari/Firefox 可离线，Edge 需联网 | 有限支持 | 个人阅读器首选，零成本 |
| **Azure Neural TTS** | 优秀（★★★★☆） | 不支持 | $16 (约 ¥115) | 不可用，需联网 | 完整支持 | 企业级高质量需求 |
| **Google Cloud TTS** | 良好（★★★★☆） | 不支持 | $20 / $24 (WaveNet) (约 ¥145-¥175) | 不可用，需联网 | 完整支持 | 多语言场景，国内访问不稳定 |
| **讯飞 TTS** | 优秀（★★★★★） | 不支持 | ¥25-¥30 (约 $3.5-$4.2) | 不可用，需联网 | 部分支持 | 国内用户最佳商业选择 |
| **阿里云 TTS** | 良好（★★★★☆） | 不支持 | ¥25 (约 $3.5) | 不可用，需联网 | 完整支持 | 国内集成，边缘部署 |

**关键发现**：
- 所有商业 TTS 均**不支持梵文/巴利文**专用语音
- Azure 免费额度：每月 50 万字符（Standard 语音）
- Google Cloud 免费额度：每月 100 万字符（Standard 语音）
- 讯飞提供免费额度，响应速度快（首包 <800ms）
- 中文音译咒语朗读场景下，Web Speech API（尤其 Edge）已能满足需求
- 若未来需要更高音质（如音频导出功能），可考虑 Azure 或讯飞作为可选后端

## 7. 结论与建议

### 7.1 推荐方案

**v2.0 采用 Web Speech API 作为默认 TTS 引擎**，理由如下：

1. **零成本**：无需 API 密钥、无调用限制、无字符计费
2. **隐私安全**：文本不上传第三方服务器（Edge 除外）
3. **离线可用**：Chrome/Safari/Firefox 完全离线运行
4. **音质可接受**：Edge 提供优秀的中文 Neural TTS，Chrome/macOS 音质中等偏上
5. **实现简单**：原生浏览器 API，无需额外依赖

### 7.2 具体实施建议

| 项目 | 建议 |
|------|------|
| **默认引擎** | Web Speech API (SpeechSynthesis) |
| **首选语音** | 按优先级：Edge Neural > macOS 系统中文 > Chrome Windows 系统中文 |
| **梵文/巴利文** | 使用中文音译文本 + 中文语音朗读 |
| **语速默认** | 0.85（用户可调范围 0.6 - 1.2） |
| **音调默认** | 0.75 |
| **断句策略** | 按中文标点分段播放，每段 200-500 字符 |
| **长文本处理** | 自动按品/段落拆分，队列播放 |
| **降级方案** | 若浏览器不支持 SpeechSynthesis，隐藏 TTS 按钮 |
| **v2.1 扩展** | 可选集成 Azure TTS 或 Edge TTS 代理作为高质量备选 |

### 7.3 不推荐方案

- **不采用 SSML**：兼容性太差，iOS Safari 完全不支持
- **不采用商业 TTS 作为默认**：成本不必要，且无梵文支持优势
- **不采用纯印地语朗读梵文**：发音偏差大，用户体验差

## 8. 对 v2.1 方案的影响

1. **TTS 服务层设计**：应在 `src/services/` 中抽象 TTS 接口（`TTSProvider`），默认实现为 `WebSpeechProvider`，预留 `AzureProvider`、`XunfeiProvider` 等扩展。接口需统一 `speak()`, `pause()`, `resume()`, `stop()`, `setRate()`, `setPitch()` 等方法。

2. **语音选择策略**：实现智能语音选择器 — 优先选择 `lang.startsWith('zh')` 的语音，按质量排序（Edge Neural > macOS 系统 > 其他）。语音列表必须通过 `voiceschanged` 事件异步获取。

3. **经文分段器**：在 `src/engine/` 中新增 `TextSegmenter` 模块，支持：
   - 按标点分割（基础模式）
   - 按语义层级分割（高级模式）
   - 咒语音译文本特殊处理
   - 每段最大长度限制（300-500 字符）

4. **诵读队列管理**：实现 `SpeechQueue` 类，管理分段播放队列，支持暂停/恢复/停止，处理 `onend`/`onerror`/`onboundary` 事件。需处理 Chrome 长文本 `onend` 不触发的已知问题（超时检测 + 重试机制）。

5. **iOS 兼容层**：针对 Safari 的 rate 参数不可靠问题，在每次 `speak()` 前强制重新设置参数。iOS 需用户手势触发首次播放。

6. **v2.1 后续规划**：
   - 可选集成 `edge-tts` 代理服务器（通过 Cloudflare Workers 等），获得免费高质量 Azure Neural 语音
   - 可选接入讯飞 TTS（国内用户性价比最高的商业方案）
   - 音频导出功能（录制 Web Speech API 输出为 WAV/MP3，使用 MediaRecorder API）
