# 验证：流式加载 + 3 种展示模式

> 任务编号：T-31
> 完成日期：2026-05-02
> 基于：docs/PROJECT_V2_PLAN.md, docs/plans/analysis/T-20-definition-display.md

## 1. 背景与目标

般若佛经阅读器 v2.0 采用"点击高亮词条后按需加载释义"的架构。用户点击经文中的佛教术语后，系统从多个启用的词典中并行查询释义，并在弹窗中流式展示。T-20 分析报告提出了 3 种展示模式（全部折叠 / 展开首个 / 全部展开）和流式加载策略。

本验证回答以下核心问题：

1. 主流词典 App（欧路词典、有道词典、Pleco 等）的释义展示方式是什么？是否支持折叠/展开模式？
2. 3 种展示模式的实际用户场景是否合理？是否覆盖了核心使用场景？
3. 展示模式设置项应存储在 IndexedDB 还是 localStorage？
4. 最终结论：维持原方案 or 调整？

## 2. 同类 App 释义展示对比

| App | 展示方式 | 加载模式 | 特点 |
|-----|----------|----------|------|
| **欧路词典** (Eudic) | 多词典分栏展示，左侧词典列表切换，右侧结果页分栏展示基础释义、搭配、同义词、例句；生词本支持一键全部展开/收起 | 本地词典一次性加载；在线释义异步加载 | 2026 最新版新增"生词本批量展开/收起"功能；解释界面支持自定义字体；跨软件取词浮动窗展示精简释义 |
| **有道词典** | Tab 切换式：网络释义（默认）、专业释义、英英释义、权威词典（柯林斯/21 世纪）、词组短语、双语例句 | 网络释义优先异步加载，点击 Tab 后加载详细内容 | 默认展示网络释义（最简版本），用户可主动切换到详细释义；多词典通过 Tab 横向切换而非垂直堆叠 |
| **Pleco** (汉英词典) | 多词典结果按频率排序垂直堆叠，每个词典条目独立展示；支持链接和交叉引用（点击汉字组成部分可跳转） | 本地词典即时加载，所有启用词典同时展示 | 无需切换词典即可看到所有词典的综合结果；结果按频率排序而非按词典分组；无折叠/展开功能，但通过搜索框快速定位 |
| **GoldenDict 3.0** | 三界面模式：高效模式（紧凑布局）、学习模式（双栏分屏）、沉浸模式（全屏）；智能分组词典管理 | 多线程搜索，百本词典秒级响应 | 启动速度提升 40%；100 本词典搜索从 1.2s 降至 0.3s；支持按语言/主题创建词典组 |
| **本项目 (v2.0)** | 卡片式垂直堆叠，每张卡片标注词典名称；3 种展示模式切换 | 流式加载，先返回先渲染 | PC 端浮动弹窗 + 移动端底部抽屉；骨架屏 + 状态图标反馈 |

### 关键发现

1. **欧路词典**：明确支持"展开/收起"操作，且在最新版中强化了"批量展开/收起"功能，说明多词典场景下用户对信息量控制有真实需求。
2. **有道词典**：采用 Tab 切换而非折叠展开，本质上是"一次只看一个词典"的设计，与本项目"多词典垂直对比"的定位不同。
3. **Pleco**：全部同时展示，无折叠功能，但其词典数量通常较少（免费版 2 个，付费版 10+），信息密度可控。
4. **GoldenDict**：通过界面模式切换来适配不同场景，与本项目"展示模式"的理念一致。

**结论**：主流词典 App 中，欧路词典和 GoldenDict 提供了类似的信息量控制机制，验证了"折叠/展开"模式在多词典场景下的合理性。

## 3. 展示模式场景分析

### 3.1 全部折叠

**适用场景**：
- 用户启用了大量词典（5+），首次点击词条时想快速浏览有哪些词典提供了释义
- 用户已知某个词条的基本含义，只想确认特定词典是否有收录
- 屏幕空间有限（移动端小屏幕）时，减少信息密度

**交互设计**：
- 每张卡片仅显示词典名徽章 + 释义摘要（前 20-30 字）+ 展开箭头
- 点击卡片或展开箭头展开该词典的完整释义
- 顶部显示"共 N 个词典有释义"的汇总信息
- 佛教经文阅读场景中，用户可能在快速浏览时只想确认"这个词在哪些词典中有解释"，而不需要立刻阅读详细内容

**风险评估**：
- 如果所有词典都折叠，用户需要额外点击才能获取信息，增加了操作成本
- 但对于"浏览型"用户（确认词条而非深度研读），这是最合适的模式

### 3.2 展开第一个

**适用场景**：
- 默认模式，平衡信息量与简洁度
- 最高优先级词典（内置词典）的释义通常已能满足 80% 的日常阅读需求
- 用户需要快速理解词条含义，同时知道还有其他词典可参考
- 佛教经文阅读的典型场景：用户读到"般若"一词，点击后首先看到内置词典的基础释义"梵语 prajñā 的音译，意为智慧"，已能继续阅读

**交互设计**：
- 第一个词典（最高优先级）完整展开释义内容
- 其余词典折叠显示摘要
- 底部显示"另有 N 个词典的释义"提示
- 支持一键切换为"全部展开"模式

**风险评估**：
- 如果第一个词典的释义过于简短或不准确，用户需要手动展开其他词典
- 但通过合理的词典优先级排序（内置词典 > 权威词典 > 用户词典），可降低此风险

### 3.3 全部展开

**适用场景**：
- 深度研读场景：用户需要对比多个词典的释义差异
- 学术研究场景：需要引用多个词典的释义进行综合分析
- 佛教术语辨析场景：某些术语在不同词典中有不同解释（如"空"在《佛学大辞典》和《中华佛教百科》中的释义侧重点不同）

**交互设计**：
- 所有词典卡片完整展开释义内容
- 长释义卡片可单独折叠（避免弹窗过长）
- 支持滚动查看所有词典内容
- 在移动端底部抽屉模式下，拖拽扩展至全屏以获得更好的阅读体验

**风险评估**：
- 如果词典数量多且释义都很长，弹窗会非常长，用户需要大量滚动
- 但这是用户主动选择的模式，且在 PC 端可以通过滚动轻松浏览

### 3.4 场景覆盖度评估

| 用户类型 | 典型行为 | 最适合的模式 | 频率 |
|----------|----------|-------------|------|
| **日常诵读者** | 边读经文边查词，快速理解术语含义 | 展开首个 | 高频（80%+） |
| **深度研读者** | 对比不同词典释义，深入理解术语 | 全部展开 | 中频（10-15%） |
| **快速浏览者** | 确认术语在哪些词典中有收录 | 全部折叠 | 低频（5-10%） |
| **学术研究者** | 需要引用多个词典的释义 | 全部展开 | 低频但高价值 |

**结论**：3 种模式覆盖了从"快速浏览"到"深度研读"的完整场景光谱，其中"展开首个"作为默认模式匹配最高频的用户行为（日常诵读）。

## 4. 设置项存储

### 4.1 候选方案对比

| 维度 | localStorage | IndexedDB |
|------|-------------|-----------|
| **API 复杂度** | 简单同步 API（`getItem/setItem`） | 异步 API，需要 Promise 封装 |
| **数据大小** | 单条最大 5MB，总量 5-10MB | 数百 MB 至数 GB |
| **读写速度** | 同步操作，极快（< 1ms） | 异步操作，较快（1-10ms） |
| **数据结构** | 仅支持字符串（需 JSON 序列化） | 支持结构化数据（对象、数组等） |
| **适用场景** | 轻量配置、偏好设置 | 业务数据、结构化存储 |
| **v2.0 规划** | 逐步废弃 | 统一结构化存储 |

### 4.2 决策分析

展示模式设置项的特点：
- **数据量极小**：仅一个字符串值（`collapse` / `expand-first` / `expand-all`）
- **读取频率高**：每次打开释义弹窗都需要读取
- **写入频率低**：仅用户切换模式时写入
- **与业务数据无关**：属于用户偏好设置，非结构化业务数据

**推荐方案：localStorage**

理由：
1. **读取速度优势**：同步 API 确保弹窗打开时无等待，不会因异步读取导致 UI 闪烁
2. **实现简单**：无需封装异步存储逻辑，代码量极少
3. **符合业界惯例**：用户偏好设置（主题、语言、展示模式等）普遍使用 localStorage
4. **v2.0 架构不冲突**：虽然 v2.0 将业务数据迁移到 IndexedDB，但用户偏好设置保留在 localStorage 是合理的分层策略

**具体实现**：

```javascript
// 读取展示模式（默认 "expand-first"）
const displayMode = localStorage.getItem('dict-display-mode') || 'expand-first'

// 保存展示模式
localStorage.setItem('dict-display-mode', mode)

// 可选：使用 Pinia store 统一管理，持久化插件同步到 localStorage
```

**扩展考虑**：如果未来需要跨设备同步用户偏好（如通过云端账号），则需要将设置项迁移到后端 API 或 IndexedDB 中。但这属于 v2.1+ 的功能，当前阶段无需过度设计。

## 5. 结论

### 明确结论：维持原方案

维持 T-20 分析报告中的设计，不做调整。理由如下：

1. **行业验证**：欧路词典最新版强化了"批量展开/收起"功能，GoldenDict 提供多界面模式切换，验证了信息量控制在多词典场景下的必要性。
2. **场景覆盖**：3 种模式（全部折叠 / 展开首个 / 全部展开）覆盖了从"快速浏览"到"深度研读"的完整场景光谱，无明显遗漏。
3. **默认模式合理**："展开首个"作为默认模式，匹配佛教经文阅读器最高频的使用场景（日常诵读中快速查词），内置词典优先展开，80% 情况下用户无需额外操作。
4. **流式加载正确**：多词典并行查询、先返回先渲染的策略，与欧路词典在线释义异步加载、GoldenDict 多线程搜索的理念一致，是减少等待感的最佳实践。
5. **存储方案清晰**：展示模式设置使用 localStorage，业务数据使用 IndexedDB，职责分离明确。

### 微调建议（非必需，可后续优化）

| 建议 | 说明 | 优先级 |
|------|------|--------|
| **自动模式记忆**：记录用户上次使用的展示模式 | 用户在深度研读时切换到"全部展开"，下次查词时自动保持该模式，减少重复操作 | P2 |
| **词典数量自适应**：仅 1 个词典时隐藏模式切换按钮 | 当查询结果仅来自一个词典时，折叠/展开无意义，可自动隐藏模式切换 UI | P2 |
| **快捷键支持**：PC 端支持键盘快捷键切换模式 | 如 `1`=折叠, `2`=展开首个, `3`=全部展开，提升效率型用户的操作体验 | P3 |

## 6. 对 v2.1 方案的影响

| 影响项 | 说明 | 优先级 |
|--------|------|--------|
| **展示模式持久化** | v2.0 实现模式切换功能，v2.1 可增加"记住上次使用的模式"功能，提升用户体验 | P2 |

| **手势操作**（移动端） | 移动端底部抽屉支持手势切换展示模式（如双指捏合切换折叠/展开） | P3 |

### 已关闭的开放问题

1. **是否需要更多展示模式？** -- 不需要。3 种模式已覆盖完整场景光谱，增加模式只会提高认知负担。
2. **是否需要为每个词典单独设置展开/折叠状态？** -- 不需要。用户场景分析表明，全局模式切换已满足需求；单独控制可通过点击单个卡片实现（在"全部折叠"模式下点击单个卡片展开）。
3. **是否需要云端同步展示模式？** -- v2.0 不需要。v2.0 为纯前端应用，无用户账号系统；若未来引入账号体系，可纳入同步范围。
