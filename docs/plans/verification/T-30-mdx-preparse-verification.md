# 验证：MDX 全部预解析 + 切割决策

> 任务编号：T-30
> 完成日期：2026-05-02
> 基于：docs/PROJECT_V2_PLAN.md, docs/plans/research/T-06-mdx-parsing.md, docs/DICTIONARY_OPTIMIZATION_DISCUSSION.md

## 1. 背景与目标

v2.0 方案中 D18 决策提出"单文件大小限制 10MB，超出想办法切割"。在后续讨论中形成了"统一预解析 + 2MB 切割"的候选方案：将所有 MDX 词典预解析后按 2MB 分块存入 IndexedDB。本验证回答以下核心问题：

1. 10 万词条的词典预解析是否可行？性能如何？
2. 切割后的查询路径是否引入了不可接受的额外开销？
3. term → chunk 路由表的构建和维护成本有多大？
4. 与 GoldenDict、欧路词典等成熟方案的对比如何？
5. 最终结论：维持原方案（分级策略）还是调整为预解析 + 切割？

## 2. 预解析性能测试

以下数据基于 T-06 调研中的公开基准测试和 MDX 格式特性推算，结合实际浏览器环境约束：

| 文件大小 | 词条数 | 预解析时间 | 结果大小(JSON) | 内存峰值 | IndexedDB 写入时间 |
|----------|--------|------------|---------------|----------|-------------------|
| 1MB | ~2,000-5,000 | 200-500ms | ~1.5-2MB | ~5-8MB | 50-150ms |
| 5MB | ~10,000-25,000 | 1-3s | ~8-10MB | ~15-25MB | 200-500ms |
| 10MB | ~25,000-50,000 | 3-10s | ~18-22MB | ~30-50MB | 500ms-1.5s |
| 20MB | ~50,000-100,000 | 10-20s | ~35-45MB | ~60-100MB | 1-3s |
| 50MB | ~100,000-250,000 | 20-60s | ~80-120MB | ~150-300MB | 3-8s |

### 2.1 10万词条预解析

以 10 万词条为基准场景（典型大型佛教词典规模，如《佛学大辞典》），对应文件约 20-30MB：

**预解析阶段**：
- mdict-js `keys()` 提取全部词条：~2-5s（受 mdict-js v10 全量 key 缓存影响）
- 逐条 `lookup()` 获取释义：100,000 / 20,000 ops/sec ≈ **5s**
- Turndown HTML → Markdown 转换：~1-3s（取决于释义 HTML 复杂度）
- **总预解析时间：8-15s**（在 Web Worker 中执行不阻塞主线程）

**存储阶段**：
- JSON 序列化结果大小：约 **35-50MB**（原始文件的 1.5-2 倍）
- IndexedDB 写入（分批事务，每批 500 条）：~1-3s
- **存储峰值内存：约 80-120MB**（原始 ArrayBuffer + JSON + 序列化缓冲）

**关键瓶颈**：
1. **浏览器内存限制**：移动端 Chrome 单标签页上限约 500MB-1GB，30MB MDX 解析峰值 100MB 以内可控，但 50MB+ 文件接近危险区
2. **IndexedDB 配额**：桌面端 Chrome 可达数 GB，移动端约 200-500MB，10 万词条存入后约占 10-25% 配额
3. **GC 压力**：`JSON.parse` 大对象后若被意外持有，V8 难以回收，需确保解析后立即释放中间变量

### 2.2 预解析 vs 直接查询的性能对比

| 操作 | 预解析模式 | 直接查询模式(mdict-js) |
|------|-----------|----------------------|
| 首次查询延迟 | < 1ms（IndexedDB get） | 5-20ms（键块解压 + 数据读取） |
| 二次查询（缓存命中） | < 0.1ms | 5-20ms |
| 首次查询（缓存未命中） | 1-5ms（IndexedDB 异步） | 5-20ms |
| 初始化时间（导入时） | 8-15s | 0.5-2s（仅解析索引） |
| 内存常驻 | JSON 数据在 IndexedDB，查询时加载 | 原文件 ArrayBuffer + 索引缓存 ≈ 5-15MB |

## 3. 切割后查询路径

### 3.1 查询流程

**预解析 + 2MB 切割方案的完整查询路径**：

```
用户点击术语 "般若"
        │
        ▼
┌─────────────────────────────────┐
│ 1. Trie 匹配确认词条存在         │  < 1ms
│    返回: { term, dictIds }      │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│ 2. 查询路由表                    │  < 1ms
│    route.get("dictId::般若")    │
│    → 返回 chunk_03              │
└──────────────┬──────────────────┘
               │
               ▼
┌─────────────────────────────────┐
│ 3. 检查内存 LRU 缓存             │  < 0.1ms
│    cache.get("chunk_03")        │
│    命中？→ 从 chunk 中提取词条    │
└──────────┬──────────────────────┘
           │ 未命中
           ▼
┌─────────────────────────────────┐
│ 4. IndexedDB 查询整个 chunk      │  1-5ms
│    chunks.get("chunk_03")       │
│    返回整个 2MB chunk 的 JSON    │
└──────────┬──────────────────────┘
           │
           ▼
┌─────────────────────────────────┐
│ 5. 从 chunk JSON 中提取目标词条  │  < 1ms
│    写入 LRU 缓存                 │
└──────────┬──────────────────────┘
           │
           ▼
┌─────────────────────────────────┐
│ 6. 渲染释义弹窗                  │  DOM 渲染时间
└─────────────────────────────────┘
```

### 3.2 性能影响

**切割带来的额外开销分析**：

| 步骤 | 无切割方案 | 2MB 切割方案 | 额外开销 |
|------|-----------|-------------|---------|
| 路由表查询 | 无 | IndexedDB get 或 Map lookup | +0.1-1ms |
| 数据读取 | 单条 get(dictId::term) | 整块 get(chunk_N) | 0ms（chunk 大小固定） |
| 数据提取 | 直接拿到释义 | 从 chunk 对象中遍历查找 | +0.5-2ms |
| 内存占用 | 单条释义 ~1-5KB | 整个 chunk ~2MB | **显著增加** |

**关键问题**：切割方案的核心缺陷在于**每次查询需要加载整个 2MB chunk 到内存**。即使用户只查看一个词条的释义（通常 1-5KB），也需要将包含该词条的 2MB 数据块全部读入内存。这意味着：

- 查询 10 个不同词条（分布在不同 chunk）：内存中可能同时存在 10 × 2MB = 20MB 的 chunk 数据
- LRU 缓存可缓解，但无法消除首次加载的 chunk 读取开销
- 与直接查询 mdict-js（单次查询仅读取目标词条的数据块，通常 < 50KB）相比，切割方案在**首次查询**时反而更重

### 3.3 路由表维护

**term → chunk 路由表的大小估算**：

以 10 万词条、按 2MB 切割（约 20 个 chunk）为例：

```javascript
// 路由表结构
const routingTable = {
  "dict-001::般若": "chunk_03",
  "dict-001::涅槃": "chunk_07",
  // ... 100,000 条
}
```

| 指标 | 数值 | 说明 |
|------|------|------|
| 路由表条目数 | 100,000 | 与词条数一致 |
| 单条大小 | ~50 bytes | key("dict-001::般若") + value("chunk_03") |
| 路由表总大小 | ~5MB | JavaScript 对象开销略高 |
| 构建时间 | 500-1000ms | 预解析完成后遍历词条生成 |
| 更新成本 | 中等 | 词条增删时需重建路由表 |

**维护成本分析**：
- 路由表需要在每次词典导入时构建，一次性成本可接受
- 但路由表本身占用 ~5MB 内存，对移动端是显著负担
- 词条增删时需重建整个路由表（或维护增量 diff），增加了实现复杂度

## 4. 同类方案对比

| 方案 | 处理方式 | 查询速度 | 内存占用 | 适用场景 |
|------|----------|----------|----------|----------|
| **本方案 v2.0（分级策略）** | <5MB 预解析，>=5MB 直接读 | <1ms(预解析) / 10-50ms(直接) | 预解析: 15-50MB / 直接: 5-15MB | 浏览器前端，移动端优先 |
| **GoldenDict 3.0** | 增量索引 + 磁盘直接读 | 220-480ms(多词典并行) | 内存优化后 ~25% 降低，最低 2GB 可运行 | 桌面端，本地文件系统 |
| **欧路词典 (Eudic)** | 原生索引 + 按需加载 | 毫秒级 | 移动端优化，支持大词库稳定运行 | 移动端 App(原生)，有文件系统访问权 |
| **MDict (原版)** | 磁盘文件直接读 | 极快(原生 C/C++) | 依赖设备存储，无内存限制 | 移动端 App(原生) |
| **MDict + 切割** | 全量预解析 + 分块存储 | <1ms(缓存命中) / 5-20ms(chunk 读取) | 路由表 5MB + chunk 缓存 2-20MB | 浏览器前端，但不推荐 |

### 4.1 GoldenDict 方案分析

GoldenDict 3.0 的核心设计：
- **增量索引**：启动时仅加载词条索引（term + 偏移量），不加载释义
- **磁盘直接读**：查询时根据索引偏移量直接读取 MDX 文件中的释义
- **多线程搜索**：多词典并发查询，查询速度提升 40%
- **内存优化**：2026 年更新后内存占用降低约 25%，最低 2GB 内存可流畅运行 20+ 词典

**关键差异**：GoldenDict 运行在桌面端，拥有完整的文件系统访问权限，可以直接随机读取 MDX 文件的任意偏移。而浏览器前端只能通过 FileReader 将整个文件加载到内存，无法实现磁盘级的随机读取。这是浏览器环境的根本限制。

### 4.2 欧路词典方案分析

欧路词典的核心设计：
- **原生应用**：拥有完整的文件系统访问和内存管理能力
- **混合存储**：基础词库内置，用户导入的 MDX 原文件存储，查询时按需解析
- **MDX 全文搜索**：v7.12.3 新增 MDX 词库全文搜索支持
- **多词库加载优化**：v7.8.9 优化多词库加载速度

**关键差异**：欧路词典是原生应用，不受浏览器沙箱限制，可以直接读取文件任意位置。浏览器前端必须在导入时做出选择：要么全量预解析，要么保留原文件用 mdict-js 查询。

## 5. 结论

**明确结论：调整为分级策略（维持 T-06 方案），不采用"统一预解析 + 2MB 切割"**

### 5.1 不采用切割方案的理由

1. **切割增加了查询复杂度但收益为负**
   - 2MB chunk 首次读取（5-20ms）比 mdict-js 单次查询（5-20ms）无明显优势
   - 路由表额外占用 ~5MB 内存，对移动端是负担而非优化
   - 每次查询需加载整个 chunk（2MB），比 mdict-js 仅读取目标数据块（<50KB）更重

2. **统一预解析的内存风险不可控**
   - 10 万词条预解析峰值内存 80-120MB，移动端可能触发 GC 甚至 OOM
   - 30MB+ 的 MDX 文件预解析 + Turndown 转换在低端设备上可能耗时 30-60s
   - IndexedDB 写入大体积 JSON 可能触发 QuotaExceededError

3. **维护成本显著增加**
   - 路由表的构建、更新、一致性维护增加了实现复杂度
   - chunk 边界调整（如 2MB → 3MB）需重新预解析整个词典
   - 用户笔记层（D10）与 chunk 边界的交互更加复杂

### 5.2 推荐方案：维持 T-06 分级策略

| 文件大小 | 处理方式 | 理由 |
|----------|----------|------|
| < 5MB | 全量预解析为 JSON 存入 IndexedDB | 解析快（<3s），查询极快（<1ms），内存可控 |
| 5-10MB | 预解析索引（term 列表），释义按需 mdict-js 查询 | 平衡内存和性能，索引 ~1-3MB |
| > 10MB | 保留 MDX 原文件，mdict-js 实时查询 + 索引预加载 | 省内存，查询延迟 10-50ms 可接受 |

**分级策略的核心优势**：
- 小词典（<5MB，占用户词典 80%+）享受极快查询体验
- 中大词典（5-10MB）在内存和性能间取得平衡
- 超大词典（>10MB）避免内存风险，查询延迟在可接受范围
- 无需路由表，无需 chunk 管理，实现复杂度低

### 5.3 D18 决策更新建议

原 D18："单文件大小限制 10MB，超出想办法切割"

**建议更新为**："单文件无硬性大小限制。上传时按文件大小自动选择处理策略（<5MB 预解析，5-10MB 索引预解析，>10MB 直接模式）。>50MB 文件提示用户可能影响性能，建议拆分或使用直接模式。"

## 6. 对 v2.1 方案的影响

基于本验证结果，对 v2.1 开发的具体影响：

1. **mdxParser.js 实现**：
   - 实现三级分级策略，不再实现 chunk 切割逻辑
   - 小词典：全量预解析 + Turndown 转 Markdown → IndexedDB
   - 中词典：仅提取 term 列表 → IndexedDB，释义通过 mdict-js 查询
   - 大词典：保留原文件 ArrayBuffer，通过 mdict-js 直接查询

2. **IndexedDB 表结构调整**：
   - `dict_entries` 表保持原有设计（key: dictId::term）
   - 小词典：直接存储所有词条的 Markdown 释义
   - 中/大词典：不存储释义，仅存储 term 列表到 `dict_index`
   - **不需要**新增 chunk 相关表

3. **不需要实现的内容**：
   - term → chunk 路由表
   - chunk 分片和重组逻辑
   - chunk LRU 缓存管理
   - chunk 边界计算算法

4. **仍需要实现的内容**：
   - 文件大小判断和分级路由
   - mdict-js 浏览器适配层（ArrayBuffer 输入）
   - Turndown HTML → Markdown 转换
   - Web Worker 中的预解析执行
   - 上传前文件检查和用户提示

5. **性能目标调整**：
   - 小词典导入时间：< 5s（含预解析 + IndexedDB 写入）
   - 中词典导入时间：< 2s（仅提取索引）
   - 大词典导入时间：< 1s（仅保存原文件）
   - 释义查询：< 1ms（小词典）/ 10-50ms（大词典）

6. **移动端兼容性**：
   - 预解析操作必须在 Web Worker 中执行，避免阻塞主线程
   - 导入大文件时提供进度条和分片解析（yield 机制）
   - 导入前检查 `navigator.storage.estimate()` 预估可用配额
