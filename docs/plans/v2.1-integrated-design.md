# v2.1 方案整合设计

> 完成日期：2026-05-02
> 基于：50 个调研任务的结论
> 状态：待评审

## 1. 背景与目标

般若佛经阅读器 v2.0 方案已完成 50 个调研任务，覆盖 Vue 3 架构、IndexedDB 存储、高亮引擎、MDX 解析、Markdown 格式、v1.0 逆向分析、前端安全、Service 层抽象和禅意设计落地等核心领域。

本方案综合所有调研结论，对比 v2.0 的差异，输出可直接指导开发的 v2.1 方案。核心目标：

1. **固化调研结论**：将 50 个调研任务的决策固化为方案文档
2. **消除 v2.0 未决项**：解决 v2.0 中 10 个待决策问题（6.1-6.10）
3. **修正方案偏差**：根据调研数据修正 v2.0 中不准确的估算和设计
4. **补充缺失模块**：增加安全策略、设计 Token 系统、Service 接口规范等 v2.0 遗漏内容

## 2. v2.0 vs v2.1 差异对比

### 2.1 架构变更

| 模块 | v2.0 方案 | v2.1 方案 | 变更原因 |
|------|-----------|-----------|----------|
| **Service 层** | JavaScript 类，直接耦合实现 | TypeScript 接口 + 工厂模式，IndexedDB/REST API 双实现 | T-48 调研确立接口抽象，支持未来后端切换 |
| **Store 大型数据** | 未明确限制 | 明确"大型数据不进入 Store"，章节内容/释义全文由 Service 层管理 | T-01 调研结论：Store 序列化后不超过 500KB |
| **Trie 构建位置** | 主线程 | Trie 构建放 Web Worker，匹配放主线程 | T-05 调研：构建 50-80ms 阻塞主线程，匹配仅 3-8ms 无需 Worker |
| **高亮渲染** | 未明确 | HTML 字符串一次性构建 + 段落懒渲染 | T-05 调研：innerHTML 比 createElement 快 10-20 倍 |
| **MDX 分级策略** | <5MB / >=5MB 两档 | <5MB / 5-10MB / >10MB 三档 | T-06 调研：5-10MB 场景需预解析索引但释义懒加载 |
| **MDX 切割** | 10MB 限制，超出切割（未实现） | 不切割，>10MB 直接模式 + 用户提示 | T-06 调研：自动切割技术风险高、实现复杂度大 |
| **存储降级** | 未提及 | 三级降级：IndexedDB → localStorage → 内存 | T-04 调研：iOS Safari 50MB 硬限、隐私模式等场景需兜底 |
| **安全策略** | 未提及 | DOMPurify + CSP + 文件验证 + 恶意扫描四层防护 | T-14 调研：用户上传 MDX 含 XSS 风险 |
| **Markdown 渲染** | marked（未确定） | markdown-it + DOMPurify | T-07 调研：markdown-it 插件生态更丰富，SSR 兼容更好 |
| **HTML→Markdown** | 未提及 | turndown + 自定义规则（保留 ruby/梵文标签） | T-06/T-07 调研：浏览器端唯一可用方案 |
| **设计 Token** | CSS 变量（v1.0 延续） | 完整 `--zen-*` Token 系统，日间/暗色/护眼三主题 | T-49 调研：v1.0 配色不合格，需禅意重构 |
| **正文字体** | 黑体 | 宋体 | T-49 调研：宋体符合传统经书风格 |
| **主题切换** | boolean `isDarkMode` | `data-theme` 属性（day/dark/eye-care） | T-49 调研：支持三种主题模式 |

|------|------|------|---------|
| Safari iOS 10.3-12.1 `onupgradeneeded` 不触发 | 低 | 高 | 检测 `webkitIndexedDB`，版本升级加 50ms 防抖 |
| Android WebView 内存压力丢弃未刷盘数据 | 中 | 高 | 关键操作写入后立即读取验证 |
| Chrome 无痕模式 IndexedDB 临时存储 | 中 | 中 | 提示用户数据不会持久化 |
| 多标签页并发读写冲突 | 低 | 中 | `versionchange` 事件通知，`blocked` 事件提示 |
