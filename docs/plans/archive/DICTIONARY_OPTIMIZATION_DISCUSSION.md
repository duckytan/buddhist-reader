# 佛经阅读器词典性能优化 - 需求讨论与决策文档

> **创建日期**: 2026-05-02
> **项目**: 般若佛经阅读器 (ai-buddhist-reader)
> **状态**: 讨论中

---

## 一、原始需求

### 1.1 核心问题

用户提出：阅读经文时，默认只加载关键词条，用于高亮匹配，不加载具体的词条解释。当用户点击该高亮词条时，再临时加载对应的解释内容，这样效率会不会更高？

### 1.2 扩展需求

1. **词典数据库化**：把所有词典做成数据库形式管理
2. **用户自定义词典**：支持用户上传自己的词典文件
3. **词典开关控制**：在设置页面，用户可以单独设置每个词典的开启/关闭状态，有些词典需要临时关闭

### 1.3 当前实现的问题

现有代码将所有词典数据（term + definition + 其他字段）在初始化时**全部加载到内存**中：

- `dictionary.js` - 内置词典（50+ 条，体积小）
- `dictionary.json`（外部）- 可能包含数万条释义
- 用户上传的词典（通过 `userDictStorage.js` 存入 IndexedDB）
- MDX 词典文件（`.mdx` 二进制格式，通过 `mdict-js` 解析）

当外部词典有数万条释义、用户又上传多个大词典时，存在以下问题：

| 问题 | 说明 |
|------|------|
| **内存占用高** | 每条释义的 `definition` 字段可能长达几百到几千字，全量加载占用大量内存 |
| **初始化慢** | 需要解析整个 JSON 文件、构建完整 Trie 树 |
| **用户词典重复加载** | 每次进入阅读页都要从 IndexedDB 读取全部数据 |
| **开关切换无反馈** | 关闭词典后，Trie 中仍包含该词典的词条，高亮不受影响 |

## 二、技术方案讨论

### 2.1 方案一：延迟加载释义

**思路**：将词典数据结构分离为两层。

```
高亮匹配阶段 → 只加载 term（关键词列表）
点击词条时  → 按需加载 definition
```

**数据结构分离**：

```javascript
// 索引层（小，用于高亮匹配）
{
  "般若": { dictIds: ["builtin", "external-1"], hasDef: true },
  "涅槃": { dictIds: ["builtin"], hasDef: true }
}

// 数据层（大，按需加载）
{
  "builtin::般若": { pinyin: "bō rě", definition: "梵语 prajñā 的音译..." },
  "external-1::般若": { source: "中华佛教百科", definition: "详细解释..." }
}
```

Trie 树只基于**索引层**的 term 构建。点击时再按 key 从数据层取出完整释义。

**优点**：
- 初始化极快，只需加载词条索引
- 内存占用大幅下降（definition 通常占总数据量 80%+）
- 用户不看释义就不加载，零浪费

**缺点**：
- 需要改造现有数据结构
- 点击释义有短暂异步加载延迟

### 2.2 方案二：数据库化（IndexedDB）

**思路**：把词典存到 IndexedDB 中，实现类似 SQLite 的结构。

```sql
-- 索引表
Table: dict_index
+--------+---------+-----------+
| term   | dict_id | has_def   |
+--------+---------+-----------+
| 般若   | builtin | 1         |
| 般若   | ext-1   | 1         |
| 涅槃   | builtin | 1         |
+--------+---------+-----------+

-- 数据表
Table: dict_entries
+------------------+--------+----------+-----------+
| key              | term   | pinyin   | definition|
+------------------+--------+----------+-----------+
| builtin::般若    | 般若   | bō rě   | 梵语...   |
| ext-1::般若      | 般若   |          | 详细解释...|
+------------------+--------+----------+-----------+
```

**优点**：
- 天然支持按需查询，不需要的数据根本不在内存
- 用户自定义词典可以直接存入，统一查询接口
- 支持增量更新、局部删除
- 可以做全文搜索（term 前缀匹配等）

**缺点**：
- IndexedDB 是异步 API，需要包装 Promise
- 首次加载索引也需要时间（但比全量快得多）
- 复杂度增加，需要处理数据库版本迁移

### 2.3 方案三：混合方案（推荐）

**思路**：结合方案一和方案二的优势，分三层存储。

```
┌─────────────────────────────────────┐
│ Layer 1: Trie 索引（内存）           │
│ 只存 term 列表，用于快速匹配高亮     │
│ 大小：通常 < 500KB                  │
├─────────────────────────────────────┤
│ Layer 2: 内置词典（内存）            │
│ 50 条核心术语，全量加载无压力       │
│ 大小：< 50KB                        │
├─────────────────────────────────────┤
│ Layer 3: 外部/用户词典（IndexedDB）  │
│ definition 按需查询，term 索引预加载│
│ 大小：无上限，按需取用              │
└─────────────────────────────────────┘
```

**工作流程**：

1. **页面初始化**：加载 Layer 1 + Layer 2 → 构建 Trie 树 → 高亮可用
2. **用户点击术语**：从 IndexedDB 查询对应 term 的 definition → 显示弹窗
3. **用户查询缓存**：已查过的释义缓存在内存中，避免重复查询
4. **用户上传词典**：解析 term 加入 Layer 1，definition 存入 IndexedDB

### 2.4 针对用户自定义词典的考虑

用户词典特点：
- 格式不统一（JSON、MDX、CSV 等）
- 大小差异大（几十条到几万条）
- 可能随时添加/删除

**建议做法**：

```javascript
// 上传时做两件事：
async function importUserDictionary(file) {
  const entries = await parseFile(file)
  
  // 1. 提取 term 加入 Trie 索引
  const terms = entries.map(e => e.term)
  await addToTrieIndex(terms)
  
  // 2. 完整数据存入 IndexedDB
  await db.bulkPut('dict_entries', entries)
}

// 点击时按需查询
async function lookupTerm(term, dictId) {
  // 先查内存缓存
  const cached = cache.get(`${dictId}::${term}`)
  if (cached) return cached
  
  // 再查 IndexedDB
  const entry = await db.get('dict_entries', `${dictId}::${term}`)
  if (entry) {
    cache.set(`${dictId}::${term}`, entry)
  }
  return entry
}
```

## 三、关键技术问题讨论

### 3.1 Trie 索引层的数据结构选型

**问题**：Trie 树应该返回什么信息？

| 选项 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **A. 最小索引** | 只存 `term → [{ dictId }]` | 极小，10万条词也能秒加载 | 点击后必须异步查数据库 |
| **B. 轻量索引** | 存 `term → [{ dictId, pinyin, category }]` | 高亮时可显示拼音，弹窗先展示基础信息 | 索引体积稍大（约全量的 30%） |

**分析**：选项 B 能提供更好的即时体验——用户点击术语后，弹窗可以先显示词条名、拼音、分类等轻量信息，释义异步加载后再追加渲染。

### 3.2 MDX 词典的处理

项目中有 `mdict-js` 和 `lzo-wasm` 依赖，说明有解析 MDX 词典的能力。MDX 是二进制格式。

| 方案 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **预解析** | 上传时转成 JSON 存 IndexedDB | 查询快，接口统一 | 存储翻倍 |
| **直接读** | 保留 `.mdx` 原文件，用 `mdict-js` 实时查询 | 省空间 | 查询稍慢，需要保持 mdict-js 依赖 |

### 3.3 多词典同词条的展示策略

当前设计：点击一个术语，可能多个词典都有释义，弹窗里全部展示。

| 策略 | 说明 | 优点 | 缺点 |
|------|------|------|------|
| **并行加载** | 同时查询所有启用的词典，等全部返回再展示 | 信息完整 | 用户等得久 |
| **流式加载** | 先展示已返回的词典释义，后续查询完成再追加 | 用户先看到内容 | 可能出现内容跳动 |

### 3.4 Trie 索引的构建时机

| 方案 | 说明 |
|------|------|
| **构建一次，持久化** | 首次打开页面时从 IndexedDB 读取 Trie，之后直接使用。更新词典时才重建。 |
| **每次启动重建** | 把 term 列表存在 IndexedDB 的简单表中，启动时读表重建 Trie。 |

### 3.5 离线场景

IndexedDB 是本地存储，断网不受影响。但如果依赖远程词典（服务器拉取释义），需要缓存策略：
- 是否需要预下载？
- 缓存过期策略？

## 四、词典开关功能讨论

### 4.1 核心问题：Trie 索引如何响应开关？

**场景**：
```
用户启用了 5 个词典，Trie 索引里有这 5 个词典的所有词条。
阅读时高亮显示所有词条。
用户在设置里关掉其中 2 个词典。
```

此时 Trie 里的词条数量**没变**，但高亮结果需要实时排除被关掉的词典。

### 4.2 方案 A：Trie 不变，运行时过滤

```javascript
// Trie 里存所有词典的所有 term（不管开关）
const matches = trie.search(text)

// 匹配后，过滤掉已关闭词典的词条
const filteredMatches = matches.filter(match => 
  match.dictIds.some(id => enabledDictIds.has(id))
)
```

| 优点 | 缺点 |
|------|------|
| 开关切换瞬间生效，不需要重建 Trie | Trie 体积始终最大，被关掉的词典的 term 仍然参与匹配计算 |

### 4.3 方案 B：Trie 只存启用词典的 term

```javascript
function toggleDict(dictId, enabled) {
  if (enabled) {
    trie.addTerms(dictTerms[dictId])  // 添加
  } else {
    trie.removeTerms(dictTerms[dictId])  // 删除
  }
}
```

| 优点 | 缺点 |
|------|------|
| Trie 体积小，只匹配需要的高亮 | Trie 需要支持动态增删 term（目前 Trie 是静态的，只支持 build）；切换开关时需要重建或局部修改，有性能开销 |

### 4.4 方案 C：分层 Trie（推荐）

```javascript
// 每个词典独立一个 Trie，按需合并匹配结果
const trieMap = {
  'builtin': new Trie(),      // 内置词典 Trie（常驻内存）
  'user-123': null,           // 用户词典 Trie（懒加载）
  'user-456': null,
}

// 搜索时，只搜索已启用的词典
function search(text) {
  const allMatches = []
  for (const [dictId, trie] of Object.entries(trieMap)) {
    if (enabledDictIds.has(dictId) && trie) {
      allMatches.push(...trie.search(text))
    }
  }
  return mergeAndDedup(allMatches)
}
```

**优点**：
- 开关切换只需改变 `enabledDictIds`，不需要动 Trie
- 关闭的词典 Trie 可以直接丢弃释放内存
- 内置词典的 Trie 始终存在，切换无延迟
- 用户词典的 Trie 可以懒加载（启用时才构建）

**缺点**：
- 多个 Trie 分别搜索，性能略有损耗（但可通过限制启用的词典数量控制）
- 需要改造现有 Trie search 接口，支持按词典维度返回

### 4.5 边界情况处理

如果用户同时启用了 10 个词典，每个都有几万条词，分层 Trie 搜索 10 次的性能如何？

**折中方案**：合并 Trie + 防抖重建

```javascript
// 用户启用词典后，动态合并为一个主 Trie
let activeTrie = null
let activeDictIds = new Set()
let rebuildTimer = null

function scheduleRebuild() {
  if (rebuildTimer) clearTimeout(rebuildTimer)
  rebuildTimer = setTimeout(() => {
    rebuildActiveTrie()
  }, 500) // 频繁切换时防抖
}
```

## 六、待解决 / 未决策问题

以下是本次讨论后仍然未解决的问题，需要在后续开发前确定：

### 6.1 Trie 索引层数据结构（未决策）

**问题**：Trie 树应该返回最小索引（仅 dictId 列表）还是轻量索引（含 pinyin、category）？

- **选项 A（最小索引）**：体积极小，但点击后必须异步查数据库才能拿到任何释义信息
- **选项 B（轻量索引）**：体积稍大（约全量 30%），但点击后可立即显示基础信息，释义异步追加

**建议倾向**：选项 B，提供更好的即时体验

### 6.2 MDX 词典处理方式（未决策）

**问题**：用户上传的 `.mdx` 文件，是预解析成 JSON 存入 IndexedDB，还是保留原文件用 `mdict-js` 实时查询？

- **预解析**：查询快，但存储空间翻倍
- **直接读**：省空间，但查询稍慢

**建议倾向**：小文件预解析，大文件（> 5MB）直接读

### 6.3 多词典同词条展示策略（未决策）

**问题**：点击术语后，多个词典的释义是并行等待全部返回再展示，还是流式加载先返回先展示？

- **并行加载**：信息完整，但等待时间长
- **流式加载**：用户体验好，但可能出现内容跳动

**建议倾向**：流式加载

### 6.4 Trie 索引构建时机（未决策）

**问题**：Trie 索引是构建一次后持久化到 IndexedDB，还是每次启动时从 term 列表重建？

- **持久化**：首次打开后复用，但更新词典时需要清理缓存
- **每次重建**：更简单可靠，但启动时间稍长

**建议倾向**：每次启动重建（简单可靠，term 列表很小，重建成本低）

### 6.5 分层 Trie vs 单一 Trie（未决策）

**问题**：是采用分层 Trie（每个词典独立 Trie）还是单一 Trie（所有词条合并）？

- **分层 Trie**：开关灵活，关闭词典可直接释放内存，但搜索性能略低
- **单一 Trie**：搜索快，但开关切换需要重建或懒标记过滤

**当前决策 D4 已选"懒标记"**，与分层 Trie 方案可以结合：使用分层 Trie，但搜索时不重建，通过 `enabledDictIds` 运行时过滤。

### 6.6 内置词典版本智能合并（需详细讨论 D13）

**问题**：内置词典从 v1 升级到 v2 时，如何与用户的"笔记层"（D10）合并？

需要考虑的场景：
- 内置词条 definition 变更，但用户写过笔记
- 内置词条被删除，但用户有笔记
- 内置新增词条，用户没有笔记

**可能的策略**：
- 内置词条只更新 `term` 和 `pinyin`，不覆盖用户笔记
- 用 checksum 判断词条是否变更，已变更的词条提示用户
- 笔记层与原始数据完全隔离，永不覆盖

### 6.7 释义格式统一转 Markdown（需详细讨论 D15）

**问题**：如何将 MDX 词典的 HTML 格式统一转为 Markdown？渲染层需要什么？

需要考虑：
- HTML → Markdown 转换库选型（`turndown`、`showdown` 等）
- Markdown 渲染库选型（`marked`、`markdown-it` 等）
- 现有 `formatDefinition` 函数的重写
- 特殊格式处理（梵文、藏文、Pali 文等需要保留特殊 class）

### 6.8 单文件 10MB 限制 + 切割（需详细讨论 D18）

**问题**：如何实现 10MB 单文件限制？超出如何切割？

切割方案候选：
