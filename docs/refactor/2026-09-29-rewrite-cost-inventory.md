## 3. 隐性资产盘点（本任务重点）

> 「看不见但很贵」的经验：代码看起来只有几百行，但背后是几十次失败尝试换来的。重建会全部丢失。

## 4. 重建的隐性收益

> ⚠️ 重要限定：**以下问题在「渐进改造」中同样可以修掉，并非重建独有优势。** 列出仅为说明「重建能顺手解决什么」，不能作为支持重建的理由。

| 问题 | 规模/证据 | 改造能否同样解决 |
|------|-----------|:---:|
| 20.8MB 词典全量内联 | `src/data/dictIndex.js` | ✅ 能（改加载策略） |
| 67MB 死资产 | `public/dict-chunks`(48MB) + `public/dict-defs`(19MB) | ✅ 能（删除） |
| 孤儿页 DictManager | `router/index.js` 无路由 | ✅ 能（接入或删除） |
| 50 处 `console.log` | `grep` 实测 50 处 | ✅ 能（清理） |
| 书签只写不读 | `stores/reader.js` | ✅ 能（补 UI） |
| 阅读时长只采集不展示 | `Reader.vue:249-259` | ✅ 能（补展示） |
| 返回来源 bug / 笔记不定位 | `Reader.vue:242`、`Notes.vue:153` | ✅ 能（小改） |
| 主题缺「日间」 | `themes.css` | ✅ 能（加一套变量） |
| 205MB 历史归档 | `archive/`（v1.0 151MB + v2.0 54MB） | ✅ 能（清理/外置） |

> 换言之：**重建的「收益」几乎全部是「顺手清理」，而非「非重建不可」**。而这些清理在改造中成本更低（不需要重写主链路）。

## 5. 重建期间的代价（隐性成本）

> 用户是**个人开发者**，无团队并行、无冗余产能。

| 代价维度 | 具体影响 | 量化 |
|----------|----------|------|
| **线上功能冻结** | 重建期间不发布新版本，用户（含作者本人）只能用旧版 | 贯穿 60~75 人天全程 |
| **旧 bug 依旧存在** | 已知问题（书签、笔记跳转、返回来源、20.8MB 首屏）在重建完成前**无法修**——因为改旧代码被视为「浪费」 | 全部已知缺陷延迟 |
| **无新功能产出** | 60~75 人天全部投入「复刻已有功能」，零新增价值 | 净负产出 |
| **重建失败风险** | 若中途放弃，两版并存、数据/文档进一步碎片化（现已有 v1/v2/v3.0-prototype 四份归档） | 沉没成本 |
| **经验断层** | 现有踩坑经验只存在于代码与 git 历史中；重建者（即使是同一人）数月后未必记得 | 见 §3，必然重现 |
| **数据兼容风险** | 用户已积累的笔记/书签/进度存于 localStorage，重建若改存储键则需迁移（v2→v3 已有此教训：IndexedDB 数据无法迁移） | 参考 `v3.0-migration-guide.md` |

**综合**：重建 = **60~75 人天的净投入 + 全程功能冻结 + 已知 bug 悬置**，换取一个「等价功能集 + 顺手清理」。而改造可在**不冻结主链路**的前提下，分模块逐步修掉同样的问题。

## 6. 改造路径的成本对照（供决策）

| 路径 | 成本 | 风险 | 产出 |
|------|------|------|------|
| **从零重建** | 60~75 人天 | 高（重踩全部坑 + 数据迁移 + 冻结期） | 等价功能 + 清理 |
| **渐进改造**（保留主链路，替换薄弱环节） | 约 15~25 人天（估） | 中（可增量验证、随时发布） | 保留隐性资产 + 修复问题 + 可加新功能 |

> 改造的切入点（供架构师细化）：词典加载策略、清理死资产/孤儿页/调试残留、补齐书签与时长闭环、统一设置数据源。**主链路（§2 的 52.7%）建议保留并局部加固，而非重写。**

## 7. 产品侧结论

**支持「渐进改造」，反对「从零重建」。**

理由：
1. **主链路占 52.7% 代码，且是全项目最成熟、返工最多的部分**——它的价值不在行数，而在 §3 的隐性资产。重建 = 丢弃 + 重踩。
2. **重建的功能侧总成本 60~75 人天**，其中 20~30 人天纯属「重现旧坑」，对个人开发者是沉重负担。
3. **重建的所谓收益（§4）在改造中同样可得，且成本更低**——没有一项是「非重建不可」。
4. **重建期间功能冻结 + 已知 bug 悬置**，对唯一开发者是纯损失。
5. 「代码过时」的实质是**局部技术债**（词典加载策略、清理项、几个未闭环功能），而非**架构性失败**——v3.0 已解决过 v2.0 的架构问题，v3.1 的痛点集中在少数可定点修复的模块。

**建议**：以「改造」为主路径，按 P0（词典加载策略、核心链路稳定化、清理死资产/孤儿页/调试残留）→ P1（书签/时长闭环、笔记定位、返回来源、设置单一数据源）→ P2（统计页、日间主题、导入、TTS/拼音）分阶段推进，全程保持可发布。
