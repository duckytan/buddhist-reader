# D13 版本智能合并分析 报告

> 任务编号：T-28
> 完成日期：2026-05-02

## 1. 背景与目标

本项目 v2.0 方案中，决策 D13 规定"内置词典版本更新时的处理"采用**智能合并**策略，但需在后续详细讨论。

本分析的目标是：研究内置词典版本更新时与用户笔记层（D10）的冲突处理策略，明确各种冲突场景下的合并规则、checksum 判断可行性、通知机制设计，并参考同类产品的冲突处理方式，最终为 v2.1 方案提供明确的版本合并策略。

**核心前提**（来自既有决策）：
- D10：用户上传词典允许添加"笔记层"，原始数据不可变，用户笔记作为附加层
- D14：同名词典重复上传创建新版本（版本链），保留历史版本
- v2.0 数据模型中，`user_notes` 表与 `dict_entries` 表分离存储，通过 `entry_key` 关联

## 2. 冲突场景分析

### 2.1 场景 1：definition 变更，有笔记

**场景描述**：内置词典从 v1 升级到 v2，某个词条（如"般若"）的 `definition` 内容发生了修改，但该词条在 `user_notes` 表中存在用户笔记。

**冲突本质**：用户的笔记是基于旧版 definition 写的，新 definition 与旧版可能存在语义差异，笔记的上下文有效性受到影响。

**合并策略**：

```
┌─────────────────────┐
│  内置 dict_entries   │  ← 更新为 v2 的新 definition
│  （不可变数据层）     │
└─────────┬───────────┘
          │
┌─────────▼───────────┐
│  user_notes 表       │  ← 保持不变，不覆盖
│  （用户笔记层）       │     标记 note.compatibility = "needs_review"
└─────────┬───────────┘
          │
┌─────────▼───────────┐
│  渲染层              │  ← 并排展示：新 definition + 用户笔记
│  展示规则            │     在笔记上方显示提示："此笔记基于旧版词典内容"
└─────────────────────┘
```

**具体规则**：
1. **永不覆盖笔记**：`user_notes` 表的数据由用户完全控制，内置词典更新绝不修改、删除用户笔记
2. **标记兼容性状态**：在 `user_notes` 表中新增 `compatibility` 字段，默认 `ok`，当关联词条的 `definition` checksum 发生变化时，标记为 `needs_review`
3. **渲染时并排展示**：新的 `definition` 正常展示，用户笔记追加在下方，但上方增加提示条：
   > "此笔记基于词典 v1 内容编写，可能与当前版本不完全匹配。[重新编辑]"
4. **提供差异对比**：用户点击"查看变化"可对比新旧 definition 的差异（见 2.4）
5. **用户可手动处理**：用户可编辑笔记、标记为"已确认适配新版"（`compatibility = "confirmed"`），或删除笔记

### 2.2 场景 2：词条被删除，有笔记

**场景描述**：内置词典 v2 删除了某个词条（如某个不常用的梵文音译），但用户在 `user_notes` 表中对该词条写过笔记。

**冲突本质**：词条从 `dict_entries` 和 `dict_index` 中消失，但 `user_notes` 中仍有引用。

**笔记保留策略**：

**规则**：**用户笔记永久保留，不因词条删除而消失**。

具体处理：

1. **笔记独立存在**：`user_notes` 表中的记录不依赖 `dict_entries` 存在。词条删除后，笔记仍然保留在数据库中
2. **高亮行为**：词条从 `dict_index` 中删除后，阅读页不再高亮该词。但用户可通过词典管理页面的"我的笔记"入口查看所有笔记（含已删除词条的笔记）
3. **笔记展示**：当用户通过其他方式（如搜索、笔记列表）打开该词条的笔记时：
   - 不显示原始 definition（因为已不存在）
   - 仅显示用户笔记内容
   - 顶部提示："此词条在当前词典版本中已移除，您的笔记已保留"
4. **用户可导出**：用户可将笔记导出为独立文件，防止未来词典变更导致笔记孤立
5. **数据库设计支持**：`user_notes` 表的 `entry_key` 字段不设置外键约束，允许引用不存在的词条

```javascript
// user_notes 表结构（扩展）
{
  id: 'note::001',
  entry_key: 'builtin::般若',     // 词条 key，无外键约束
  note: '我的理解...',
  compatibility: 'ok',            // ok | needs_review | confirmed | orphaned
  original_checksum: 'abc123...', // 笔记创建时的词条 checksum
  created_at: '2026-05-01',
  updated_at: '2026-05-02',
}

// 当词条被删除后，compatibility 标记为 orphaned
// 笔记仍然可查询，只是不再与高亮关联
```

### 2.3 场景 3：新增词条，无笔记

**场景描述**：内置词典 v2 新增了词条，用户在 `user_notes` 表中没有该词条的笔记。

**策略**：**自动添加，无需用户干预**。

具体规则：

1. **自动加入索引**：新词条自动写入 `dict_index` 表，Trie 索引在下次启动时自动重建（v2.0 方案 6.4 决策）
2. **自动加入释义**：新词条的 definition 写入 `dict_entries` 表
3. **阅读页高亮**：新词条在阅读页自动高亮，与现有词条无区别
4. **无通知打扰**：不弹通知告知用户"新增了 X 个词条"——符合"简单、专注、不打扰"的核心理念
5. **词典管理页可见**：在词典管理页的词典详情中，显示"v2 新增 X 条"，用户可主动查看

```
┌──────────────────────────────────────┐
│  内置词典 v2.0                       │
│  50 条 · 官方 · 已更新               │
│                                      │
│  v1 → v2 变更：                      │
│  · 新增 12 条                        │
│  · 修改 3 条                         │
│  · 删除 1 条                         │
│                                      │
│  [查看变更详情]                      │
└──────────────────────────────────────┘
```

### 2.4 场景 4：部分重叠

**场景描述**：内置词条在新版本中 definition 内容部分重叠——既有保留的内容，也有新增/修改的内容，而用户在该词条上写过笔记。

**差异对比策略**：

采用 Git 风格的文本差异对比（diff），在词典弹窗中提供"版本对比"功能：

1. **差异可视化**：使用 Markdown diff 语法展示变更
   - 绿色标记：新增内容
   - 红色标记：删除内容
   - 无标记：保留内容

2. **对比入口**：在词典弹窗中，当检测到词条 definition 有变更且用户有笔记时，在笔记提示条旁显示"[查看变化]"按钮

3. **对比展示格式**：
   ```
   ┌──────────────────────────────────────┐
   │  般若 (bō rě)                        │
   ├──────────────────────────────────────┤
   │  v1 → v2 变更：                      │
   │                                      │
   │   梵语 prajñā 的音译，意为"智慧"。    │
   │ - 在佛教中指超越世俗的洞察力。        │  (删除)
   │ + 在佛教中指超越世俗的洞察力，        │  (修改)
   │ + 即"究竟智慧"或"实相智慧"。          │
   │ + 与"方便"(upaya)并列为菩萨修行的     │  (新增)
   │ + 两大核心要素。                      │
   │                                      │
   │  ───────────────────────────────     │
   │  📝 您的笔记：                        │
   │  我的理解...                          │
   │                                      │
   │  [重新编辑笔记]  [标记已适配]         │
   └──────────────────────────────────────┘
   ```

4. **差异粒度**：以段落/句子为单位对比，不按字符级 diff（佛教释义通常是大段文字，字符级差异可读性差）
5. **技术实现**：使用 `diff` 库（如 `diff-match-patch` 或 `jsdiff`）生成差异，前端用不同颜色渲染

## 3. checksum 可行性

### 3.1 original_checksum 字段设计

在 `dict_entries` 表中为每个词条增加 `checksum` 字段：

```javascript
{
  key: 'builtin::般若',
  term: '般若',
  pinyin: 'bō rě',
  definition: '梵语 prajñā...',
  checksum: 'sha256-abc123...',  // definition 内容的哈希
  _version: 2,                     // 词典版本号
}
```

### 3.2 判断词条是否变更的流程

```
内置词典 v1 → v2 更新
        │
        ▼
遍历新版本的 dict_entries
        │
        ▼
对每个词条：
  1. 计算新 definition 的 checksum
  2. 查询旧版本中同 key 的 checksum
  3. 比较：
     - checksum 相同 → 词条未变
     - checksum 不同 → 词条已修改
     - 新词条（旧版本无记录）→ 新增
     - 旧词条（新版本无记录）→ 已删除
        │
        ▼
生成变更清单：
  { added: [...], modified: [...], removed: [...] }
```

### 3.3 可行性分析

| 维度 | 评估 | 说明 |
|------|------|------|
| **准确性** | 高 | SHA-256 对 definition 文本内容做哈希，任何字符变更都能检测到 |
| **性能** | 低开销 | 仅在词典更新时计算一次，不运行时计算 |
| **存储** | 可忽略 | 每个词条增加 64 字节（hex 编码的 SHA-256），50 条约 3.2KB |
| **碰撞风险** | 极低 | SHA-256 碰撞概率在实际场景中可忽略 |
| **维护成本** | 低 | 更新时自动计算，无需手动维护 |

### 3.4 注意事项

1. **checksum 范围**：仅对 `definition` 字段计算哈希，不包括 `term`、`pinyin`、`category` 等元数据字段。因为笔记关联的是释义内容，元数据变更不影响笔记有效性
2. **空值处理**：如果 `definition` 为空，checksum 计算空字符串的哈希（`e3b0c44...`），确保一致性
3. **多词典场景**：不同词典的同一词条各自有独立的 checksum，互不影响
4. **用户词典**：用户导入的词典也使用同样的 checksum 机制，在版本链（D14）中用于判断变更

### 3.5 结论

**完全可行**。`original_checksum` 是判断词条定义是否变更的可靠方案，存储开销极小，实现简单，且与现有数据模型天然兼容。

## 4. 通知机制

### 4.1 通知原则

遵循项目核心理念"简单、专注、不打扰"：

- **不主动弹窗打断**：词典更新后不弹出全屏通知
- **被动发现**：在用户正常使用过程中（如点击词条、打开词典管理页）感知变更
- **关键信息前置**：在受影响最大的场景（阅读页点击词条）中展示提示

### 4.2 通知位置与方式

| 场景 | 通知方式 | 内容 |
|------|----------|------|
| **阅读页点击词条** | 词典弹窗内提示条 | "词典已更新至 v2，此词条内容与旧版有差异" |
| **词典管理页** | 词典卡片徽章 | "已更新"徽章 + 变更摘要 |
| **设置页首次打开** | 顶部信息条（仅一次） | "词典已更新，您的 X 条笔记可能需要检查。[查看详情]" |
| **笔记编辑页** | 笔记上方提示 | "此笔记基于词典 v1 内容编写" |

### 4.3 通知内容设计

**词典弹窗内的提示**（最核心场景）：

```
┌──────────────────────────────────────┐
│  ⚡ 般若 (bō rě) · 核心术语          │
│  ──────────────────────────────────  │
│  梵语 prajñā 的音译，意为"智慧"...   │
│  （新的 definition）                  │
│                                      │
│  ┌────────────────────────────────┐  │
│  │ ⚠️ 词典已更新至 v2             │  │
│  │ 此词条内容与旧版有差异。        │  │
│  │ 您的笔记可能与新内容不匹配。    │  │
│  │ [查看变化] [重新编辑] [忽略]   │  │
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

**[忽略]** 按钮：标记该词条的笔记为 `compatibility = "confirmed"`，不再显示提示。

**词典管理页的变更摘要**：

```
┌──────────────────────────────────────┐
│  📖 内置词典                    [ON] │
│  50 条 · 官方 · 已更新               │
│                                      │
│  上次更新：2026-05-02                │
│  v1.0.0 → v2.0.0                    │
│  · 新增 12 条                        │
│  · 修改 3 条（其中 1 条有您的笔记）   │
│  · 删除 1 条                         │
│                                      │
│  [查看变更详情]                      │
└──────────────────────────────────────┘
```

### 4.4 通知生命周期

1. **更新时记录**：词典更新时，在 `dict_config` 表中记录 `last_updated_at` 和 `update_summary`
2. **用户查看后标记**：用户点击"查看变化"或"忽略"后，在 `user_notes` 中标记 `compatibility = "confirmed"`
3. **全局通知消退**：当所有受影响笔记都被标记为 `confirmed` 后，设置页顶部的信息条自动消失

## 5. 同类 App 对比

| App | 冲突处理 | 特点 |
|-----|----------|------|
| **Obsidian** | 文件级冲突解决 | 提供两种策略：(1) 智能合并 — 基于 AST 对文档进行合流比对，无法自动解决的冲突使用 Git 样式的冲突标记（`<<<<<<< HEAD`）让用户手动选择；(2) 时间戳强制覆盖 — 以最新修改为准。核心是纯 Markdown 文件的冲突解决，适用于多设备同步场景 |
| **Notion** | 操作级实时合并 | 基于 Operational Transformation / CRDT 的实时协作，多个用户同时编辑同一页面时自动合并。数据库字段级别的修改不会互相覆盖。不支持版本间的"智能合并"，只有操作日志回滚 |
| **本方案** | 数据层分离 + checksum 差异检测 | 原始数据（`dict_entries`）与用户笔记（`user_notes`）物理隔离，永不互相覆盖。通过 checksum 检测变更，提示用户手动确认。核心是"保护用户数据"而非"自动合并" |

### 对比分析

| 维度 | Obsidian | Notion | 本方案 |
|------|----------|--------|--------|
| **冲突模型** | 多设备编辑同一文件的写入冲突 | 多人同时编辑同一页面的并发冲突 | 内置数据更新与用户笔记的语义冲突 |
| **自动合并** | 支持（基于 AST 的智能合并） | 支持（基于 CRDT 的实时合并） | **不支持**（主动选择不自动合并） |
| **用户介入** | 仅在自动合并失败时 | 一般不需要 | 始终需要（用户决定是否修改笔记） |
| **数据保护** | 历史版本 + 回收站 | 页面历史 + 操作日志 | 笔记层与数据层完全隔离 |
| **适用性** | 纯文本文件，结构统一 | 结构化数据库 + 富文本块 | 结构化词典词条 + 自由文本笔记 |

### 为什么本方案不采用自动合并

1. **语义层面**：词典 definition 是语义内容，不是纯文本代码。自动 diff + merge 可能产生语义不连贯的结果
2. **用户意图**：用户笔记是个人理解，不是对原内容的"补充注释"，自动合并没有意义
3. **数据隔离**：D10 已明确原始数据不可变，笔记作为附加层，两者物理隔离是最安全的策略
4. **简单可靠**：不引入复杂的合并算法，降低实现复杂度和维护成本

## 6. 结论与建议

### 6.1 版本合并策略

**核心原则：数据层分离 + checksum 变更检测 + 用户主动确认**

| 场景 | 策略 | 用户干预 |
|------|------|----------|
| definition 变更，有笔记 | 保留笔记，标记 `needs_review`，并排展示 | 用户可选择编辑/确认/忽略 |
| 词条被删除，有笔记 | 笔记永久保留，标记 `orphaned` | 用户可导出或删除笔记 |
| 新增词条，无笔记 | 自动加入索引和释义 | 无需干预 |
| 新增词条，有笔记 | 不适用（词条不存在时笔记无法创建） | — |
| 部分重叠 | 提供 diff 对比视图 | 用户可查看变化后决定是否修改笔记 |

### 6.2 数据库变更建议

为支持版本合并策略，需在 v2.0 数据模型基础上做以下扩展：

```sql
-- dict_entries 表新增字段
ALTER TABLE dict_entries ADD COLUMN checksum TEXT;     -- definition 的 SHA-256
ALTER TABLE dict_entries ADD COLUMN _version INTEGER;   -- 词典版本号

-- user_notes 表新增字段
ALTER TABLE user_notes ADD COLUMN compatibility TEXT;         -- ok | needs_review | confirmed | orphaned
ALTER TABLE user_notes ADD COLUMN original_checksum TEXT;     -- 笔记创建时的词条 checksum
ALTER TABLE user_notes ADD COLUMN reviewed_at DATETIME;       -- 用户确认适配的时间

-- dict_config 表新增字段
ALTER TABLE dict_config ADD COLUMN last_updated_at DATETIME;  -- 上次更新时间
ALTER TABLE dict_config ADD COLUMN update_summary JSON;       -- {added: N, modified: N, removed: N}
```

### 6.3 实现优先级

| 优先级 | 功能 | 所属阶段 |
|--------|------|----------|
| P0 | `checksum` 字段 + 计算逻辑 | Phase 3（词典版本管理） |
| P0 | 笔记层不覆盖逻辑 | Phase 3（用户笔记层） |
| P1 | 兼容性标记 + 提示展示 | Phase 3（用户笔记层） |
| P1 | 变更摘要生成 | Phase 3（词典版本管理） |
| P2 | diff 对比视图 | Phase 3 后续迭代 |
| P2 | 笔记导出功能 | Phase 3 后续迭代 |

## 7. 对 v2.1 方案的影响

本分析结果对 v2.1 方案的具体影响如下：

1. **数据模型扩展**：`dict_entries` 需增加 `checksum` 字段，`user_notes` 需增加 `compatibility` 和 `original_checksum` 字段。这些字段在 Phase 3 实现时需一并加入

2. **词典更新流程**：在 `DictService.importDict()` 中需新增版本对比逻辑：
   - 计算新词条 checksum
   - 与旧版本对比生成变更清单
   - 更新受影响笔记的 `compatibility` 状态

3. **词典管理页**：需在词典卡片上展示"已更新"状态和变更摘要，新增"查看变更详情"入口

4. **词典弹窗组件**：需在释义卡片中支持兼容性提示条的渲染，包含"查看变化"、"重新编辑"、"忽略"三个操作按钮

5. **diff 对比组件**：需新增独立的差异对比组件，用于展示词条新旧 definition 的变化
