# 词条高亮匹配 分析报告

> 任务编号：T-19
> 完成日期：2026-05-02
> 基于：docs/PROJECT_V2_PLAN.md, docs/plans/research/T-05-highlight-engine.md

## 1. 背景与目标

般若佛经阅读器 v2.0 需要在经文正文中对词典词条进行高亮标记，使用户在阅读时能够直观识别佛教术语。高亮匹配是高亮引擎的前端入口，直接决定了哪些文本片段会被渲染为高亮样式。

核心目标：
- **匹配准确性**：正确识别词典中的所有词条，不遗漏、不误判
- **重叠处理**：当多个词条覆盖同一段文本时（如 "般若" 和 "般若波罗蜜多"），按合理策略去重
- **性能达标**：千字经文匹配响应 < 50ms（T-05 目标）
- **多词典区分**：同一词条来自不同词典时，高亮样式可区分
- **禅意风格**：高亮颜色柔和、不刺眼，与经文正文禅意风格协调

本分析覆盖匹配规则、嵌套词条处理、匹配边界、高亮样式、多词典区分五个维度。

## 2. 匹配规则

### 2.1 精确匹配

**核心策略：基于 Trie 树的精确字符串匹配，不做任何模糊化处理。**

佛教经文的术语高亮与普通搜索不同，它不需要"近似匹配"——词典里有什么词条，就高亮什么。模糊匹配反而会导致误判（如将非术语的普通文字误认为术语）。

**匹配流程**：

```
输入经文文本 → Trie 逐字扫描 → 收集所有命中 → 贪心长词优先去重 → 返回匹配列表
```

**逐字扫描实现**（与 T-05 方案一致）：

```javascript
// Trie.search(text) 伪代码
function search(text) {
  const matches = []
  for (let i = 0; i < text.length; i++) {
    let node = this.root
    for (let j = i; j < text.length; j++) {
      const char = text[j]
      if (!node.children.has(char)) break
      node = node.children.get(char)
      if (node.isEnd) {
        // 命中一个词条
        const term = text.slice(i, j + 1)
        matches.push({
          term,
          start: i,
          end: j + 1,
          length: j + 1 - i,
          dictIds: [...node.dictIds],
        })
      }
    }
  }
  return matches
}
```

**关键特性**：
- 从文本每个字符位置出发，沿 Trie 下行匹配
- 每遇到 `isEnd` 标记的节点，即命中一个词条
- 长词和短词都会被收集（如同时命中 "般若" 和 "般若波罗蜜多"）
- 去重在后处理阶段完成（见第 3 节）

**为何不做分词**：T-05 已论证——经文高亮不需要语义分词，词典词条即匹配模式。分词器的歧义处理（如"双向最大匹配"、"HMM 模型"）对高亮场景无价值。

### 2.2 模糊匹配

**结论：v2.0 不需要模糊匹配。**

| 模糊匹配类型 | 是否适用 | 原因 |
|-------------|---------|------|
| 编辑距离（Levenshtein） | 否 | 佛经术语拼写固定，不存在"拼错"的概念 |
| 拼音模糊 | 否 | 经文是汉字文本，拼音高亮无意义 |
| 部分匹配（子串） | 否 | Trie 天然支持子串匹配（从任意位置开始） |
| 正则表达式 | 否 | 词典是离散词条列表，不是模式串 |
| 通配符（*、?） | 否 | 用户不会上传含通配符的词典 |

**v2.1 可能的扩展**（本期不做）：
- **简繁混排匹配**：用户词典含繁体词，经文为简体，需简繁转换后再匹配。可在 Trie 构建时将简繁变体同时插入
- **异体字匹配**：佛经中常见的异体字（如 "无"/"無"、"够"/"夠"），同样可在构建时插入变体

## 3. 嵌套词条处理

### 3.1 重叠场景分类

佛教词典中词条重叠主要有以下三种场景：

| 类型 | 示例 | 发生频率 |
|------|------|---------|
| **前缀重叠** | "般若" 与 "般若波罗蜜多" | 高 |
| **后缀重叠** | "波罗蜜多" 与 "蜜多时"（假设后者是词条） | 低 |
| **交叉重叠** | "菩萨" 与 "萨埵" 部分重叠 | 极低 |

前缀重叠是最常见的场景——短词是长词的前缀。后缀重叠和交叉重叠在佛经词典中极少出现。

### 3.2 去重策略：贪心长词优先

**算法**（与 T-05 方案一致）：

```javascript
function deduplicateLongestFirst(matches) {
  // 按 start 升序，同 start 时按 length 降序
  matches.sort((a, b) =>
    a.start - b.start || (b.end - b.start) - (a.end - a.start)
  )

  const result = []
  let lastEnd = 0
  for (const m of matches) {
    if (m.start >= lastEnd) {
      result.push(m)
      lastEnd = m.end
    }
  }
  return result
}
```

**处理效果**：

```
经文: "观自在菩萨行深般若波罗蜜多时"
原始匹配:
  { term: "观自在",     start: 0, end: 3 }
  { term: "菩萨",       start: 3, end: 5 }
  { term: "般若",       start: 7, end: 9 }
  { term: "般若波罗蜜多", start: 7, end: 13 }

去重后:
  { term: "观自在",       start: 0, end: 3 }   ← 保留
  { term: "菩萨",         start: 3, end: 5 }   ← 保留
  { term: "般若波罗蜜多", start: 7, end: 13 }  ← 保留（长词优先）
  // "般若" 被 "般若波罗蜜多" 覆盖，舍弃
```

### 3.3 前缀重叠的正确性保证

贪心算法对**前缀重叠**场景 100% 正确：

- 短词和长词共享同一个 `start` 位置
- 排序后长词排在短词前面（length 降序）
- 长词先被选中，`lastEnd` 更新到长词末尾
- 短词的 `start` < `lastEnd`，被跳过

对**交叉重叠**（如 "菩萨" 和 "萨埵"），贪心算法选择先出现的词条，这种行为是可接受的——因为交叉重叠在佛经词典中极少出现，且两种选择在语义上无显著差异。

### 3.4 多词典同位置匹配

当同一位置的同一词条来自多个词典时，不去重，而是合并 `dictIds`：

```javascript
// 匹配结果示例
{
  term: "般若",
  start: 7,
  end: 9,
  dictIds: ["builtin", "user-001"],  // 多词典合并
}
```

这在 Trie 节点层面自然实现——每个节点的 `dictIds` 数组记录了所有包含该词条的词典 ID。

### 3.5 嵌套高亮的 UX 决策

**不渲染嵌套高亮**（即不在 "般若波罗蜜多" 的高亮内部再嵌套 "般若" 的高亮），原因：
- 视觉上嵌套高亮会产生色块叠加，干扰阅读
- 点击时用户期望点击的是完整词条，而非子串
- T-05 颜色方案中已有"多词典重叠"（淡紫色）处理多词典场景

**点击行为**：用户点击 "般若波罗蜜多" 时，弹窗中展示该词条在所有词典中的释义，而非 "般若" 和 "般若波罗蜜多" 两个词条。

## 4. 匹配边界

### 4.1 标点符号处理

**核心原则：匹配不区分标点，但高亮渲染时不包含标点。**

Trie 匹配逐字扫描，遇到标点字符时，由于标点不在 Trie 中，自然失配回退到根节点——这是正确的行为，不需要特殊处理。

**但需关注的边界场景**：

| 场景 | 经文示例 | 匹配行为 | 处理 |
|------|---------|---------|------|
| 标点紧跟词条 | "菩萨，行深..." | "菩萨" 在 "，" 前结束 | 自然处理，无需干预 |
| 标点夹在词条中间 | "般若-波罗蜜多"（假设含连字符） | 不会匹配到 "般若波罗蜜多" | 正确行为——原文确实被标点隔断 |
| 全角/半角标点 | "菩萨。行深" vs "菩萨.行深" | 均不影响匹配 | Trie 只匹配中文字符 |

### 4.2 空格处理

佛经正文中可能出现空格（如排版分隔）：

```
"观自在 菩萨 行深 般若波罗蜜多时"
```

**处理方式**：
- 匹配时空格字符不在 Trie 中，自然失配
- 渲染高亮时，`start`/`end` 指向字符位置，不受空格影响
- 不需要 trim 或预处理——保留原文空格

### 4.3 换行符处理

经文分段时可能含换行符（`\n`、`\r\n`）：

**处理方式**：
- 按段落拆分后分别匹配（T-05 方案 B：段落分块 + 懒渲染）
- 每个段落独立调用 `trie.search(paragraphText)`
- 跨段落的词条不会匹配——这在佛经中几乎不存在（术语不会跨段落）

### 4.4 特殊字符过滤

佛经中可能出现以下特殊字符：

| 字符类型 | 示例 | 处理 |
|---------|------|------|
| 章节标记 | `--- 第一章 ---` | 不匹配，不渲染高亮 |
| 注音符号 | `般若（bō rě）` | 括号内的拼音不会匹配到词典词条 |
| 梵文转写 | `prajñā` | 拉丁字符不在 Trie 中，不匹配 |
| Emoji/装饰符 | 无 | 现代佛经一般不含 |

**无需过滤**——Trie 本身已经天然过滤了非中文字符。

### 4.5 匹配范围限制

**不匹配以下区域**：
- 经文标题（书名）
- 译者信息
- 章节标题
- 脚注/注释文本
- 用户笔记内容

实现方式：高亮引擎仅对经文正文段落文本调用匹配，标题和元数据在渲染时单独处理，不经过 Trie 扫描。

## 5. 高亮样式

### 5.1 颜色方案

基于 T-05 的 4 色映射方案，结合禅意风格微调：

| 词典类型 | 颜色（浅色模式） | 颜色（深色模式） | 用途 | 色值来源 |
|---------|----------------|----------------|------|---------|
| **内置词典** | `#FFF3E0` (暖橙黄) | `#5D4037` (深棕) | 核心术语，最常用 | 禅意暖色调 |
| **官方扩展词典** | `#E0F2F1` (淡青) | `#004D40` (深青) | 中华佛教百科等权威词典 | 清凉色 |
| **用户上传词典** | `#F1F8E9` (淡绿) | `#33691E` (深绿) | 个人笔记、自定义词典 | 草木色 |
| **多词典重叠** | `#F3E5F5` (淡紫) | `#4A148C` (深紫) | 同一术语被多个词典覆盖 | 莲花色 |

**与 T-05 方案的差异**：将内置词典从 `#FFF3CD`（偏黄的 Bootstrap 警告色）调整为 `#FFF3E0`（更暖的橙黄），更符合佛经阅读器的禅意美学。

### 5.3 辅助视觉元素

除背景色外，提供以下可选辅助视觉元素（通过设置开关控制）：

| 元素 | 默认 | 说明 |
|------|------|------|
| 下划线（虚线） | 关闭 | `border-bottom: 1px dashed`，提示可点击 |

### 5.4 样式可访问性

- 所有配色组合的对比度 >= 3:1（WCAG AA 级别）
- 不单独依赖颜色传递信息（多词典重叠词条同时带有 `[data-multi]` 属性和 `aria-label`）
- 深色模式下自动反转颜色

## 6. 多词典同词条区分

### 6.1 场景定义

当同一词条 "般若" 同时出现在多个词典中时：

```
内置词典:     般若 → 梵语 prajñā 的音译...
官方扩展词典: 般若 → 般若（prajñā），佛教核心概念...
用户词典:     般若 → 我的个人理解...
```

需要解决两个问题：
1. **匹配阶段**：如何知道该词条被哪些词典覆盖？
2. **渲染阶段**：高亮样式如何区分？

### 6.2 匹配阶段：dictIds 合并

Trie 节点天然支持多词典标记：

```javascript
class TrieNode {
  children = {}
  isEnd = false
  dictIds = []  // 包含此词条的所有词典 ID
}
```

匹配结果中，`dictIds` 数组记录了所有覆盖该词条的词典：

```javascript
{
  term: "般若",
  start: 7,
  end: 9,
  dictIds: ["builtin", "official-encyclopedia", "user-001"],
}
```

### 6.3 渲染阶段：高亮颜色决策

**决策矩阵**：

| dictIds 数量 | 渲染策略 | 示例 |
|-------------|---------|------|
| 1 个词典 | 使用该词典对应的颜色 | `["builtin"]` → 暖橙黄 |
| 2+ 个词典 | 使用多词典重叠色（淡紫） | `["builtin", "user-001"]` → 淡紫 |
| 0 个词典 | 不渲染高亮（理论上不会出现） | — |

**data 属性设计**：

```html
<!-- 单词典 -->
<span class="highlight-term" data-dict="builtin" data-term="般若">般若</span>

<!-- 多词典 -->
<span class="highlight-term" data-dict="multi" data-term="般若"
      data-dict-ids='["builtin","user-001"]'>般若</span>
```

### 6.4 点击交互：多词典释义展示

用户点击高亮词条时（无论单词典还是多词典），统一弹出释义弹窗（T-20 方案）：

- 弹窗顶部显示词条名、拼音、分类
- 下方卡片式展示各词典释义，每张卡片标注词典名称和类型
- 流式加载：先返回的词典释义先渲染（T-05 方案 + T-20 确认）
- 多词典场景默认使用"展开首个"模式（D5 决策）

### 6.5 词典优先级排序

当多词典覆盖同一条目时，弹窗中词典卡片的排序：

1. **内置词典**（最高优先级）
2. **官方扩展词典**（按词条数降序）
3. **用户上传词典**（按启用时间倒序，最近启用的在前）

排序依据：权威性和用户关注度。

### 6.6 词典标识徽章

每张释义卡片左上角显示词典标识：

| 词典类型 | 图标 | 标签 | 标签颜色 |
|---------|------|------|---------|
| 内置词典 | `📖` | "内置" | 橙色 |
| 官方扩展 | `📚` | "官方" | 青色 |
| 用户词典 | `📁` | "个人" | 绿色 |

## 7. 结论与建议

### 7.1 高亮匹配方案总结

| 维度 | 方案 | 理由 |
|------|------|------|
| **匹配算法** | Trie 逐字精确匹配 | 无需模糊匹配，佛经术语固定 |
| **分词策略** | 不分词，直接扫描 | T-05 已论证，高亮不需要语义理解 |
| **重叠去重** | 贪心长词优先 | 对前缀重叠 100% 正确，O(n log n) 性能好 |
| **标点处理** | 自然失配，不特殊处理 | Trie 不含标点字符，自动回退 |
| **匹配范围** | 仅经文正文段落 | 标题、注释不参与匹配 |
| **高亮颜色** | 4 色映射 + 禅意暖色调 | 区分词典来源，风格协调 |
| **嵌套渲染** | 不嵌套，长词覆盖短词 | 视觉清晰，交互一致 |
| **多词典区分** | 单词典用类型色，多词典用重叠色 | 点击后弹窗区分各词典释义 |

### 7.2 实现模块分工

| 模块 | 职责 | 参考文档 |

| `components/dict/DefinitionPopup.vue` | 释义弹窗（多词典展示） | T-20 |

### 7.3 性能指标确认

| 指标 | 目标值 | 达成路径 |
|------|--------|---------|
| 构建时间（10万词条） | < 100ms | Web Worker 构建，不阻塞主线程 |
| 匹配响应（1000字） | < 50ms | Trie O(n*m)，约 3-8ms |
| 匹配响应（5000字） | < 50ms | Trie O(n*m)，约 15-30ms |
| 去重耗时 | < 5ms | 贪心排序 O(n log n)，命中数通常 < 200 |
| HTML 生成 | < 10ms | 字符串拼接，比 createElement 快 10-20 倍 |
| 渲染耗时（千字） | < 50ms | innerHTML + 段落懒渲染 |

### 7.4 开放问题

| 问题 | 建议 | 优先级 |
|------|------|--------|
| 简繁混排匹配 | 构建 Trie 时同时插入简繁变体 | v2.1 |
| 异体字匹配 | 同上，维护异体字映射表 | v2.1 |
| 高亮密度过高 | 提供"仅高亮核心术语"模式（仅 builtin 词典） | v2.0 设置页 |
| 批量高亮开关 | 全部词典关闭时高亮消失（D8），但保留虚线下划线提示 | v2.0 |

## 8. 对 v2.1 方案的影响

| v2.0 决策 | 对 v2.1 的影响 |
|-----------|---------------|
| **精确匹配（无模糊）** | v2.1 若需简繁/异体字匹配，需在 Trie 构建层增加变体插入逻辑，不改动匹配算法 |
| **贪心长词优先** | 算法稳定，v2.1 无需变更。若未来需要"显示所有命中"（非去重），需新增 `deduplicate: false` 选项 |
| **4 色映射方案** | v2.1 若词典类型增加（如社区共享词典），需扩展颜色映射表（建议预留 2 个颜色槽位） |
| **不渲染嵌套高亮** | v2.1 可探索"悬停显示子词条"功能：鼠标悬停在长词高亮上时，tooltip 提示包含的短词条 |
| **段落分块匹配** | v2.1 需确认段落拆分策略（按 `<p>` 标签、按固定字数、还是按语义段落） |
| **Trie 逐字扫描** | 若 v2.1 词典规模达到 50 万+ 词条，需评估是否切换为 AC 自动机（T-05 5.3 已留备选） |
| **HTML 字符串渲染** | v2.1 若引入 Vue 组件化高亮（替代 innerHTML），需重新评估渲染性能 |
| `data-dict-ids` 属性 | v2.1 的释义弹窗可直接读取此属性，无需重新查询词典信息，减少一次 IndexedDB 查询 |
