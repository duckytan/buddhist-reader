# 经书导入功能 分析报告

> 任务编号：T-25
> 完成日期：2026-05-02
> 基于：docs/PROJECT_V2_PLAN.md

## 1. 背景与目标

v2.0 项目方案中 `SutraService.importSutra(file, metadata)` 接口已定义但尚未实现。当前 v1.0 的经书数据硬编码在 `sutras.js` 中，无法动态扩展。用户需要自行导入 txt 格式的佛经文本，包括网上下载的经文、个人整理的讲义等。

**目标**：设计一套轻量、可靠的经书导入流程，支持用户将本地 txt 文件导入为可阅读的经书，包含自动章节分割、元数据提取、重复检测和导入回滚等能力。设计需符合"简单、专注、不打扰"的核心理念。

**核心使用场景**：
1. 用户在书架页面点击"导入经书"，选择本地 txt 文件
2. 系统自动解析文件，提取经名、译者等元数据
3. 自动识别章节结构并生成目录
4. 检测是否与已有经书重复，给出处理建议
5. 导入完成后可在书架中看到新经书并阅读

## 2. 支持格式

| 格式 | 处理方式 | 验证规则 |
|------|----------|----------|
| **txt** | 读取全文 → 编码检测 → 元数据提取 → 章节分割 → 存入 IndexedDB | 编码必须为 UTF-8 或 GBK（自动转换）；文件大小上限 20MB；不可为空文件；至少包含 100 字有效内容 |
| **utf-8 BOM** | 自动剥离 BOM 头后处理 | BOM 头 (`EF BB BF`) 在读取后自动去除，不影响后续解析 |

**不支持的格式（v2.0）**：epub、pdf、docx 等。这些格式需要额外的解析库，会增加打包体积。可在 v2.1 考虑。

**编码处理策略**：
- 优先按 UTF-8 读取
- 若出现乱码特征（连续替换字符），尝试 GBK 解码
- 使用 `TextDecoder` API 原生支持，无需额外依赖

## 3. 章节分割

### 3.1 分割策略：正则自动匹配为主，用户手动调整为辅

佛经 txt 文件的章节标记有多种常见格式，需要覆盖以下模式：

**一级正则规则（佛经专用，优先级最高）**：

| 模式 | 正则表达式 | 示例 |
|------|-----------|------|
| 卷/品/分 | `^(第[零一二三四五六七八九十百千\d]+[卷品分])\s*(.*)` | "第一品 序品"、"第二卷" |
| 会/部 | `^(第[零一二三四五六七八九十百千\d]+[会部])\s*(.*)` | "第一会" |
| 章/节 | `^(第[零一二三四五六七八九十百千\d]+[章节])\s*(.*)` | "第一章 缘起" |
| 回（章回体） | `^第[零一二三四五六七八九十百千\d]+回\s+(.*)` | "第一回 灵鹫山中" |

**二级正则规则（通用小说格式，备选）**：

| 模式 | 正则表达式 | 示例 |
|------|-----------|------|
| 数字编号 | `^([\d]+)[、.．]\s*(.*)` | "1、引言"、"2. 正文" |
| 纯数字 | `^(\d+)\s+(.*)` | "1 序分" |

**完整正则**（合并多模式，启用 multiline 和 unicode 标志）：

```javascript
const CHAPTER_PATTERNS = [
  // 佛经专用：卷、品、分、会、部
  /^第[零一二三四五六七八九十百千\d]+[卷品分]\s*.+$/gmu,
  // 佛经专用：会、部
  /^第[零一二三四五六七八九十百千\d]+[会部]\s*.+$/gmu,
  // 通用：章、节
  /^第[零一二三四五六七八九十百千\d]+[章节]\s*.+$/gmu,
  // 章回体
  /^第[零一二三四五六七八九十百千\d]+回\s+.+$/gmu,
  // 数字编号
  /^[\d]+[、.．]\s*.+$/gmu,
];
```

### 3.2 分割流程

```
读取 txt 全文
    │
    ▼
剥离 BOM 头（如有）
    │
    ▼
按行分割文本
    │
    ▼
逐行匹配章节正则（从高优先级到低优先级）
    │
    ▼
收集章节标题及位置偏移
    │
    ▼
┌── 匹配到 0 个章节？ ──→ 整篇文章作为单章 ──┐
│                                          │
│ 匹配到 1 个章节？ ──→ 检查是否在文件开头   │
│   ├─ 在开头 → 整篇作为单章（可能是标题行） │
│   └─ 不在开头 → 前面的内容作为"前言"       │
│                                          │
│ 匹配到 2+ 个章节？ ──→ 正常分割            │
└──────────────────────────────────────────┘
```

### 3.3 正则 vs 手动配置 对比

| 方案 | 优点 | 缺点 | 推荐 |
|------|------|------|------|
| **纯正则自动匹配** | 零配置，用户无感知；对标准格式经文效果好 | 非标准格式可能误判或漏判 | 首选 |
| **用户手动指定分割符** | 100% 准确 | 增加用户操作成本，体验差 | 备选 |
| **正则 + 预览确认** | 兼顾自动化与准确性 | 增加一个确认步骤 | **推荐方案** |

**推荐方案：正则自动匹配 + 导入前预览确认**

用户在导入时，系统自动识别章节后展示预览卡片：
- 显示识别到的章节数量
- 列出前 5 个章节标题供用户确认
- 提供"调整"入口（v2.1 支持手动编辑章节分割点）
- 用户确认后才真正写入 IndexedDB

### 3.4 章节标题提取注意事项

- **全角空格处理**：佛经中常见全角空格（`\u3000`）分隔标题，正则中需兼容
- **全角冒号**：`：` vs `:`，都需要支持
- **无空格标题**：如"第一品序品"中间无空格也需匹配
- **BOM 头影响**：首行 `^` 锚点可能被 BOM 干扰，需先剥离

## 4. 元数据提取

### 4.1 提取策略

txt 文件没有结构化元数据，需要从文件内容中智能推断：

**提取源优先级**：

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 1 | 文件名 | `般若波罗蜜多心经.txt` → 经名 = "般若波罗蜜多心经" |
| 2 | 文件首行/前几行 | 佛经常以经名或"如是我闻"开头 |
| 3 | 正则匹配元数据行 | 如 "译者：玄奘"、"唐 玄奘译" |
| 4 | 用户手动填写 | 自动提取失败时回退 |

### 4.2 经名提取

```javascript
const SUTRA_NAME_PATTERNS = [
  // 文件名去除扩展名（最可靠）
  fileName => fileName.replace(/\.[^.]+$/, ''),
  // 首行匹配：以"佛说"、"般若"等开头
  /^(\S{2,30}(?:经|咒|偈|论|律))$/,
  // 标题行：《经名》
  /^《(.{2,30}(?:经|咒|偈|论|律)?)》/,
  // 带"佛说"前缀
  /^(佛说.{2,25}(?:经|咒|偈))$/,
];
```

**经名清洗规则**：
- 去除首尾空白
- 去除常见的后缀如 `_txt`、`_txt8`、`(1)` 等下载标记
- 去除卷数信息如"卷一"、"上卷"（卷数单独提取）

### 4.3 译者提取

佛经译者信息有固定模式：

```javascript
const TRANSLATOR_PATTERNS = [
  // 标准格式：朝代 + 译者 + 译
  /^([东西南北]?[晋唐宋元明清汉魏齐梁陈隋唐]+)\s*·?\s*(.+?)\s*译$/,
  // 简化格式：xxx 译
  /^(.+?)\s*译$/,
  // 多人合译：xxx、xxx 译
  /^(.+?)\s*、\s*(.+?)\s*译$/,
  // 失译
  /^失译$/,
  /^失译人名$/,
];
```

常见朝代前缀：`后汉`、`姚秦`、`东晋`、`刘宋`、`唐`、`宋`、`元魏`、`曹魏`、`萧齐`、`陈` 等。

### 4.4 卷数提取

```javascript
const VOLUME_PATTERNS = [
  // "X卷"
  /(\d+)\s*卷/,
  // "第X卷"
  /第([零一二三四五六七八九十百千\d]+)\s*卷/,
  // 文件名含卷数
  /(?:^|[_\s])(\d+)卷?(?:[_\s]|$)/,
];
```

## 5. 重复检测

### 5.1 检测维度

| 维度 | 匹配方式 | 处理策略 |
|------|---------|---------|
| **精确匹配** | 经名完全相同 + 译者相同 | 提示"已存在相同经书"，建议跳过 |
| **同名不同译者** | 经名相同 + 译者不同 | 提示"存在同名但不同译者的版本"，允许作为新版本导入 |
| **近似匹配** | 经名相似度 > 0.8（去除标点、空格后） | 提示"可能存在相似经书"，由用户决定是否继续 |
| **内容匹配** | 前 200 字内容 MD5 比对 | 检测是否为同一经书的不同排版 |

### 5.2 同名不同译者的处理

这是佛经阅读器特有的场景。例如：
- 《金刚经》鸠摩罗什译本 vs 玄奘译本
- 《心经》玄奘译本 vs 法月译本

**处理方案**：
1. 检测到同名经书时，列出已有的译者版本
2. 显示新导入的译者信息
3. 提供三个选项：
   - **"添加为新版本"**：保留为独立的经书条目，经名后追加译者标识，如 `金刚经（鸠摩罗什译）`
   - **"覆盖"**：替换已有经书（需二次确认）
   - **"取消导入"**：放弃本次导入

### 5.3 经书 ID 生成规则

```javascript
function generateSutraId(title, translator) {
  // 基础 ID：经名拼音/简化
  let base = slugify(title);  // 如 "xin-jing"

  // 如果存在同名不同译者，追加译者标识
  if (translator) {
    const translatorSlug = slugify(extractTranslatorName(translator));
    base = `${base}-${translatorSlug}`;  // 如 "jin-gang-jing-jiu-mo-luo-shi"
  }

  // 确保唯一性：如果 ID 已存在，追加序号
  if (sutraExists(base)) {
    let i = 1;
    while (sutraExists(`${base}-${i}`)) i++;
    base = `${base}-${i}`;
  }

  return base;
}
```

### 6.2 失败回滚机制

IndexedDB 事务天然支持回滚。导入时使用一个事务包裹所有写入操作：

```javascript
async function importSutra(file) {
  const tx = db.transaction(['sutra_index', 'sutra_content'], 'readwrite');

  try {
    // 1. 写入经书索引
    await tx.objectStore('sutra_index').put(sutraRecord);

    // 2. 写入所有章节内容
    for (const chapter of chapters) {
      await tx.objectStore('sutra_content').put(chapter);
    }

    await tx.done; // 全部成功才提交

    // 3. 写入成功后构建 Trie 索引
    await buildTrieForSutra(sutraRecord.id);
  } catch (error) {
    // 事务自动回滚：sutra_index 和 sutra_content 都不会写入
    tx.abort();
    throw new ImportError(`导入失败: ${error.message}`);
  }
}
```

**回滚场景覆盖**：
- 章节内容写入部分失败 → 整批回滚
- Trie 索引构建失败 → 经书数据已写入但标记为 `load_status: error`，用户可重试
- 浏览器存储空间不足 → 捕获 `QuotaExceededError`，提示用户清理空间

### 6.3 大文件解析性能优化

对于万字以上的经文（如《法华经》约 7 万字、《华严经》约 80 万字），需要避免主线程阻塞：

**策略分级**：

| 文件大小 | 处理方式 |
|----------|----------|
| < 1MB（约 50 万字以内） | 主线程直接处理，耗时 < 500ms |
| 1MB - 5MB | 使用 Web Worker 异步处理，显示进度条 |
| > 5MB | 提示用户文件过大，建议分割（上限 20MB 硬性限制） |

**Web Worker 方案**：
```javascript
// 主线程
const worker = new Worker(new URL('./sutraImportWorker.js', import.meta.url));
worker.postMessage({ file: fileObject });

worker.onmessage = (e) => {
  if (e.data.type === 'progress') {
    updateProgressBar(e.data.percent);
  } else if (e.data.type === 'result') {
    handleImportResult(e.data.sutra);
  } else if (e.data.type === 'error') {
    handleImportError(e.data.error);
  }
};
```

**Worker 内部**：
1. 使用 `FileReader.readAsText()` 读取文件
2. 逐行扫描匹配章节（避免一次性 `split('\n')` 产生大数组）
3. 将章节列表和元数据回传主线程
4. 主线程负责写入 IndexedDB（Worker 无法直接访问 IndexedDB 的 sync API）

## 7. 同类 App 对比

### 7.1 微信读书

| 维度 | 微信读书体验 |
|------|-------------|
| **支持格式** | txt、epub、pdf、doc、docx |
| **导入方式** | 本地文件选择、微信聊天导入、网页版上传、文件管理器分享 |
| **章节识别** | 自动识别，基于正则匹配"第X章"等模式 |
| **章节准确度** | 标准格式识别率高；无章节标记的文本无法自动分割 |
| **元数据提取** | 从文件名提取书名；无译者等高级元数据 |
| **重复处理** | 相同文件名的书籍视为不同版本，同时存在于书架 |
| **大文件处理** | 支持大文件，但有上传大小限制（网页版 100MB） |
| **排版** | 导入后自动智能排版，适配阅读器界面 |
| **不足** | 无法手动调整章节分割；txt 无封面图 |

### 7.2 掌阅 iReader

| 维度 | 掌阅 iReader 体验 |
|------|------------------|
| **支持格式** | txt、epub、pdf、chm、umd、ebk 等 |
| **导入方式** | 本地扫描、WIFI 传书、文件管理器打开 |
| **章节识别** | "智能断章"功能，基于关键词（第X章、第X节等）自动识别 |
| **章节准确度** | 关键词匹配，存在误判（正文中含"第X章"字样时被误识别为章节） |
| **元数据提取** | 仅从文件名提取书名 |
| **重复处理** | 同文件名的书籍合并，新版本覆盖旧版本 |
| **大文件处理** | 支持大文件，txt 自动二次排版 |
| **特色功能** | 内置格式转换引擎，TXT 导入后自动生成目录导航 |
| **不足** | 误判率较高；无法手动编辑目录 |

### 7.3 多看阅读

| 维度 | 多看阅读体验 |

### 7.4 对比总结与借鉴

| 借鉴点 | 来源 | 我们的方案 |
|--------|------|-----------|
| 多格式导入入口 | 微信读书 | v2.0 仅支持 txt，入口为书架页"导入"按钮 |

## 8. 结论与建议

### 8.1 经书导入方案

**最终方案**：

| 组件 | 方案 | 理由 |
|------|------|------|
| 支持格式 | 仅 txt（v2.0） | 保持轻量，佛经最常见的纯文本格式 |
| 章节分割 | 佛经专用正则 + 通用正则组合 | 覆盖"卷、品、分、会、章、节、回"等佛经标记 |
| 元数据提取 | 文件名优先 + 内容正则匹配 + 手动填写回退 | 最大化自动提取，失败时不阻断流程 |
| 重复检测 | 经名 + 译者 + 内容前缀 MD5 | 处理同名不同译者的佛经特有场景 |
| 大文件处理 | < 1MB 主线程，1-5MB Web Worker，> 5MB 提示 | 兼顾性能和用户体验 |
| 导入预览 | 识别结果确认卡片 | 差异化体验，让用户有控制权 |
| 回滚机制 | IndexedDB 事务 + 状态标记 | 确保数据一致性 |

### 8.2 数据结构补充

在 v2.0 方案的 `sutra_index` 表中补充字段：

```
Table: sutra_index (经书索引)
┌──────────────┬──────────┬──────────────┬──────────┬─────────────┬──────────┬──────────┐
| id (PK)      | title    | translator   | volume   | chapters    | load_status | source   |
├──────────────┼──────────┼──────────────┼──────────┼─────────────┼─────────────┼──────────┤
| xin-jing     | 心经     | 玄奘译       | null     | 1           | ready       | builtin  |
| user-001     | 金刚经   | 鸠摩罗什译   | null     | 32          | ready       | import   |
└──────────────┴──────────┴──────────────┴──────────┴─────────────┴─────────────┴──────────┘

新增字段:
- translator: 译者信息
- volume: 卷数
- source: 来源（builtin | import）
- importTime: 导入时间（仅 source=import 时）
- originalFileName: 原始文件名
- fileSize: 文件大小（字节）
```

### 8.3 技术要点

1. **正则引擎**：使用 JavaScript RegExp 的 `multiline` + `unicode` 标志
2. **BOM 处理**：读取后检测并剥离 `\uFEFF` 和 `EF BB BF`
3. **编码转换**：优先 UTF-8，失败时尝试 GBK
4. **事务写入**：IndexedDB 的 `readwrite` 事务包裹所有写入
5. **Worker 通信**：File 引用通过 `postMessage` 传递，Worker 内部用 FileReader 读取

## 9. 对 v2.1 方案的影响

| 影响项 | 说明 | 优先级 |
|--------|------|--------|
| **手动章节编辑** | v2.0 仅支持自动识别，v2.1 可增加导入后手动调整章节边界的功能 | P2 |
