# 验证：D18 切割方案可行性

> 任务编号：T-34
> 完成日期：2026-05-02
> 基于：docs/PROJECT_V2_PLAN.md, docs/plans/research/T-06-mdx-parsing.md, docs/plans/verification/T-30-mdx-preparse-verification.md

## 1. 背景与目标

D18 决策提出"单文件大小限制 10MB，超出想办法切割"。本验证针对该决策中的"切割"方案进行可行性分析，回答以下问题：

1. 10MB MDX 文件解析后的实际数据量膨胀系数是多少？
2. 2MB 切割边界的精确控制方式：按条累加 vs 按大小切分，哪个更优？
3. 超大单条释义（>2MB）如何处理？
4. `dict_term_lookup` 路由表的大小和查询性能如何？
5. 切割后两步查询（lookup → entry）的总耗时能否 < 2ms？
6. 对比：是否需要引入 5MB 分界点（小文件预解析，大文件保留原文件）？
7. 最终结论：维持原方案（分级策略）还是调整？

## 2. 数据膨胀系数

MDX 文件解析为 JSON 后，数据量会显著膨胀。膨胀主要来源于：

- **解压膨胀**：MDX 内部使用 GZIP/LZO 压缩，解压后体积增大
- **格式转换**：二进制结构 → JSON 文本，增加了键名、引号、缩进等开销
- **HTML 转 Markdown**：Turndown 转换后，部分标签转为 Markdown 语法，体积变化不大但结构更冗长

| 原始大小 | 解析后大小(JSON) | 膨胀系数 | 典型词条数 | 备注 |
|----------|-----------------|----------|------------|------|
| 1MB | 1.5-2MB | 1.5x - 2.0x | 2,000-5,000 | 小型词典 |
| 5MB | 8-10MB | 1.6x - 2.0x | 10,000-25,000 | 中型词典 |
| 10MB | 18-22MB | 1.8x - 2.2x | 25,000-50,000 | 大型词典 |
| 20MB | 35-45MB | 1.75x - 2.25x | 50,000-100,000 | 超大型词典 |

**关键发现**：
- 膨胀系数与词条平均释义长度正相关：释义越长（HTML 标签越多），膨胀系数越高
- 佛教词典通常释义较长（含梵文注音、多义项解释），膨胀系数偏向 **1.8x - 2.2x** 区间
- 10MB 原始文件解析后约 **18-22MB**，已超出 IndexedDB 单条记录的建议上限

## 3. 切割方案对比

### 3.1 按条累加切割

**原理**：逐条累加词条的 JSON 大小，当累计接近 2MB 时切块。

```
词条1 (50KB) + 词条2 (80KB) + ... + 词条N (30KB) ≈ 2MB → 切为 chunk_01
词条N+1 (60KB) + ... → 切为 chunk_02
```

| 优点 | 缺点 |
|------|------|
| 保证每个 chunk 大小不超过 2MB | 单条释义可能超过 2MB（边界情况无法处理） |
| 切块粒度精确，内存可控 | 需要预解析所有词条大小才能确定边界，增加解析轮次 |
| 路由表构建简单（term → chunkId） | 相邻词条语义无关，LRU 缓存命中率低 |

**核心问题**：需要**两轮解析**——第一轮计算每条大小并确定边界，第二轮按边界切块。这在浏览器环境中意味着 10MB MDX 需要解析 2 次，总时间翻倍。

### 3.2 按大小切分

**原理**：按固定条数（如每 1000 条）切块，不关心实际大小。

```
词条1-1000 → chunk_01
词条1001-2000 → chunk_02
```

| 优点 | 缺点 |
|------|------|
| 实现简单，一轮解析即可完成 | chunk 大小不均匀（短释义 chunk 可能仅 500KB，长释义 chunk 可能 > 5MB） |
| 不需要预计算大小 | 某些 chunk 可能远超 2MB 限制，失去切割意义 |
| 相邻词条可能有语义关联，LRU 缓存命中率略高 | 路由表需要额外记录 chunk 大小范围 |

**核心问题**：无法保证每个 chunk 在 2MB 以内，切割失去内存控制的意义。

### 3.3 对比结论

| 维度 | 按条累加 | 按大小切分 |
|------|----------|------------|
| 实现复杂度 | 高（两轮解析） | 低（一轮解析） |
| 内存控制精度 | 精确（≤2MB） | 不精确（可能超限） |
| 解析时间 | 2x | 1x |
| 路由表大小 | 与词条数一致 | 与词条数一致 |
| LRU 缓存命中率 | 低 | 中 |

**两种方案都有明显缺陷**，且都引入了额外的复杂度和性能开销。

## 4. 超大释义处理

MDX 词典中，部分词条的释义可能非常大（如"般若"、"涅槃"等核心佛教术语，释义可能包含数千字的详细解释、引用经文、图片引用等）。

**极端场景**：单条释义 > 2MB

| 处理方式 | 优点 | 缺点 |
|----------|------|------|
| **单独存储**：将超大释义作为独立 chunk | 保证 chunk 大小可控 | 路由表需要特殊标记，查询逻辑复杂化 |
| **压缩存储**：对超大释义使用额外压缩 | 减少体积 | 查询时需额外解压，增加延迟 |
| **保留原文件引用**：超大释义不预解析，通过 mdict-js 实时查询 | 避免预解析膨胀 | 查询路径不一致，需要特殊处理 |
| **拆分释义**：将长释义按段落拆分 | 均匀分布 | 破坏释义完整性，渲染时需要重组 |

**推荐方案**：对于 > 2MB 的单条释义，**保留原文件引用 + mdict-js 实时查询**。这类词条占比极低（< 0.1%），不影响整体体验。

## 5. 路由表评估

切割方案需要维护 `term → chunkId` 的路由表。以典型佛教词典规模评估：

| 词典大小 | 词条数 | 路由表条目数 | 路由表大小 | 构建时间 | 查询耗时 | 备注 |
|----------|--------|-------------|-----------|---------|---------|------|
| 1MB | 2,000-5,000 | 2,000-5,000 | 100-250KB | 50-100ms | < 0.1ms | 小型词典 |
| 5MB | 10,000-25,000 | 10,000-25,000 | 500KB-1.2MB | 200-500ms | < 0.5ms | 中型词典 |
| 10MB | 25,000-50,000 | 25,000-50,000 | 1.2MB-2.5MB | 500-1000ms | < 1ms | 大型词典 |

**路由表查询路径**：

```
用户点击术语 "般若"
    │
    ▼
1. 查询路由表: route.get("dictId::般若") → "chunk_03"    < 0.1ms (Map lookup)
    │
    ▼
2. 检查 LRU 缓存: cache.get("chunk_03") → 未命中
    │
    ▼
3. IndexedDB 查询: chunks.get("chunk_03") → 返回 2MB JSON  1-5ms
    │
    ▼
4. 从 chunk JSON 中提取目标词条                                < 1ms
    │
    ▼
5. 写入 LRU 缓存，渲染释义弹窗
```

**两步查询总耗时**：
- 缓存命中：< 0.5ms（路由表 lookup + 内存提取）
- 缓存未命中：**2-6ms**（路由表 lookup + IndexedDB 读取 + JSON 解析 + 词条提取）

**关键问题**：缓存未命中时，**每次查询需要加载整个 2MB chunk**。这意味着：
- 查询 10 个不同词条（分布在 10 个 chunk）：内存中可能同时存在 10 × 2MB = **20MB** 的 chunk 数据
- 即使用户只查看一个词条（1-5KB），也需要将整个 chunk 读入内存
- 与 mdict-js 直接查询（仅读取目标数据块，通常 < 50KB）相比，**切割方案在首次查询时反而更重**

## 6. 5MB 分界点方案对比

引入 5MB 分界点的分级策略（T-06 方案）与切割方案对比：

| 维度 | 切割方案（全量预解析 + 2MB 切割） | 分级策略（5MB 分界点） |
|------|----------------------------------|----------------------|
| **< 5MB 词典** | 预解析 → 切割 → 路由表 → 多 chunk 查询 | 全量预解析 → 单条查询 |
| **5-10MB 词典** | 预解析 → 切割 → 路由表 → 多 chunk 查询 | 仅预解析索引 → mdict-js 按需查询 |
| **> 10MB 词典** | 预解析 → 切割 → 路由表 → 多 chunk 查询 | 保留原文件 → mdict-js 实时查询 |
| 实现复杂度 | 高（切割逻辑 + 路由表 + chunk 管理） | 中（仅分级路由） |
| 查询延迟（小词典） | < 0.5ms（缓存命中）/ 2-6ms（未命中） | < 1ms（IndexedDB 单条查询） |
| 查询延迟（大词典） | 2-6ms（但 chunk 读取量大） | 10-50ms（mdict-js 查询） |
| 内存占用 | 路由表 1-2.5MB + chunk 缓存 2-20MB | 索引 1-3MB（大词典不加载释义） |
| 维护成本 | 高（chunk 边界调整需重解析） | 低（仅文件大小判断） |
| 移动端兼容性 | 差（chunk 缓存占用大） | 好（按需加载，内存可控） |

**分级策略的核心优势**：
1. 小词典（<5MB，占用户词典 80%+）享受极快查询体验，无需切割
2. 中大词典在内存和性能间取得平衡，无需预解析全部释义
3. 超大词典避免内存风险，查询延迟在可接受范围
4. **无需路由表，无需 chunk 管理，实现复杂度显著降低**

## 7. 结论

**明确结论：调整为分级策略，不采用"10MB 限制 + 2MB 切割"方案**

### 7.1 不采用切割方案的理由

1. **切割增加了查询复杂度但收益为负**
   - 2MB chunk 首次读取（2-6ms）比 IndexedDB 单条查询（< 1ms）或 mdict-js 查询（10-50ms）无明显优势
   - 路由表额外占用 1-2.5MB 内存，对移动端是负担而非优化
   - 每次查询需加载整个 chunk（2MB），比 mdict-js 仅读取目标数据块（< 50KB）更重

2. **全量预解析的内存风险不可控**
   - 10MB MDX 解析后膨胀至 18-22MB，峰值内存 30-50MB
   - 移动端 Chrome 单标签页上限约 500MB-1GB，多词典场景下可能触发 GC 甚至 OOM
   - IndexedDB 写入大体积 JSON 可能触发 QuotaExceededError

3. **维护成本显著增加**
   - 路由表的构建、更新、一致性维护增加了实现复杂度
   - chunk 边界调整需重新预解析整个词典
   - 超大释义（> 2MB）需要特殊处理逻辑
   - 用户笔记层（D10）与 chunk 边界的交互更加复杂

### 7.2 推荐方案：分级策略（5MB 分界点）

| 文件大小 | 处理方式 | 理由 |
|----------|----------|------|
| < 5MB | 全量预解析为 JSON 存入 IndexedDB | 解析快（< 3s），查询极快（< 1ms），内存可控 |
| 5-10MB | 预解析索引（term 列表），释义按需 mdict-js 查询 | 平衡内存和性能，索引 ~1-3MB |
| > 10MB | 保留 MDX 原文件，mdict-js 实时查询 + 索引预加载 | 省内存，查询延迟 10-50ms 可接受 |

### 7.3 D18 决策更新建议

原 D18："单文件大小限制 10MB，超出想办法切割"

**建议更新为**：

> "单文件无硬性大小限制。上传时按文件大小自动选择处理策略：<5MB 全量预解析，5-10MB 索引预解析 + 释义按需查询，>10MB 保留原文件 + mdict-js 实时查询。>50MB 文件提示用户可能影响性能，建议拆分。"

## 8. 对 v2.1 方案的影响

基于本验证结果，对 v2.1 开发的具体影响：

1. **mdxParser.js 实现**：
   - 实现三级分级策略，**不实现 chunk 切割逻辑**
   - 小词典：全量预解析 + Turndown 转 Markdown → IndexedDB
   - 中词典：仅提取 term 列表 → IndexedDB，释义通过 mdict-js 查询
   - 大词典：保留原文件 ArrayBuffer，通过 mdict-js 直接查询

2. **IndexedDB 表结构调整**：
   - `dict_entries` 表保持原有设计（key: dictId::term）
   - 小词典：直接存储所有词条的 Markdown 释义
   - 中/大词典：不存储释义，仅存储 term 列表到 `dict_index`
   - **不需要**新增 chunk 相关表和路由表

3. **不需要实现的内容**：
   - term → chunk 路由表
   - chunk 分片和重组逻辑
   - chunk LRU 缓存管理
   - chunk 边界计算算法
   - 超大释义单独存储方案

4. **仍需要实现的内容**：
   - 文件大小判断和分级路由
   - mdict-js 浏览器适配层（ArrayBuffer 输入）
   - Turndown HTML → Markdown 转换
   - Web Worker 中的预解析执行
   - 上传前文件检查和用户提示

5. **性能目标**：
   - 小词典导入时间：< 5s（含预解析 + IndexedDB 写入）
   - 中词典导入时间：< 2s（仅提取索引）
   - 大词典导入时间：< 1s（仅保存原文件）
   - 释义查询：< 1ms（小词典）/ 10-50ms（大词典）

6. **移动端兼容性**：
   - 预解析操作必须在 Web Worker 中执行，避免阻塞主线程
   - 导入大文件时提供进度条和分片解析（yield 机制）
   - 导入前检查 `navigator.storage.estimate()` 预估可用配额
